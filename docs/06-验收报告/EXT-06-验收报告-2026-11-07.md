### 1.3 判定口径（本报告的自限规则）

1. **「通过」** 须同时满足：AC 文本标注"自动化"或"自动化+手工"中的自动化部分，且相关断言由**本次实际执行**的单测覆盖并全绿；AC 若含 UI 交互，则对应 UI 行为须在代码中完整可定位（给出 `文件:行`），且**不存在可指认的需求偏差**。UI 呈现本身未上机的，在该条备注中注明（不影响"通过"判定）。
2. **「通过（代码通过，真机待验）」** 用于：实现完整、单测覆盖、代码走查无偏差，但 AC 明确要求的**真机行为**（系统通知触达时序、精确闹钟、重启恢复、真机播放与抓包）本次无法执行。该档**不计入"部分通过"**，但必须在灰度发布/上架前按 §2 步骤补验；补验失败立即降级并登记 BUG。
3. **「部分通过」** 用于：① 手工/真机步骤本次**未执行**且无法用代码走查替代；② 需求文本与实现存在可指认的偏差；③ AC 明确给出的性能指标**无实测数据**。**凡未执行的手工项，一律不计入"通过"**。
4. 每条 AC 的"验证方法"均为可照做的操作路径或命令，用户可据此独立复验。
5. 严重级沿用评审口径：**P0** = 契约不一致 / 安全 / 崩溃 / 数据错误；**P1** = 可靠性缺陷 / 明显功能缺陷 / 需求覆盖缺失；**P2** = 可维护性、文案与文档类建议。
