## 2. 缺陷清单

> 严重度定义：**P0** = 阻断验收/数据正确性；**P1** = 影响主要功能或明显体验缺陷，须尽快修；**P2** = 一般缺陷/健壮性；**P3** = 建议/优化。

### REV-01（P0）`withTx` 内嵌套自开事务导致外层事务提前提交，写操作丧失原子性

- **文件:行号**：`src/services/backupService.ts:344`（`historyRepo.save(record)`）、`src/db/index.ts:81-108`（`withTx`）、`src/db/repositories/historyRepo.ts:45-47`
- **问题**：`importData()` 在 `withTx(['sources','favorites','history'], …)` 回调里对每条历史调用 `historyRepo.save(record)`，而 `historyRepo.save` **不接受 `tx` 参数、内部自开 `withTx(['history'])`**。IndexedDB 事务在回调 `await` 一个非本事务的 IDB 请求期间会**自动提交**（这正是 `src/db/index.ts:5-7` 注释里自己写明的约束）。
- **实测证据（CDP 探针，真实 Chrome + dev server）**：
  - 同构最小复现：外层 `withTx(['sources','history'])` 内先 `put` 源 A → 调 `historyRepo.save()` → 再 `put` 源 B，结果 `put B` 抛 `InvalidStateError: The transaction has finished`，而 **A 与 history 均已落库**（`{ steps: [... 'source B put THREW: InvalidStateError'], sources: 2, history: 1 }`）。
  - 真实调用路径：`backupService.importData(backup, 'overwrite')` 导入 1 源 + 3 历史，`withTx` 全程未报错、`report={sources:1,history:3}`，但外层 `sources`+`favorites` 的 `clear()`/`put` 与 `history` 写入实际分属不同事务，**不是单事务**。
- **影响**：AC-90「导入非法 JSON/版本不符时不修改任何现有数据」在**部分失败路径**上会被破坏——一旦后续写入抛错，前面已提交的数据无法回滚（`withTx` 的 `tx.abort()` 已无意义）。FR-40/AC-89 的"整体恢复"在异常时可能留下半套数据。
- **建议**：`historyRepo.save` 增加可选 `tx` 参数（与 `favoriteRepo.save/saveMany`、`mediaRepo.save` 一致），`backupService` 传入外层 `tx`；或改为 `sourceStore`/`favoriteRepo` 同款 `saveMany(records, tx)` 批量写。同时在 `withTx` 内增加开发期断言（检测 `tx.done` 已 settle 时 `console.error`），避免同类问题再次静默。
- **对应**：FR-40、AC-89、AC-90；技术方案 5 章、API-13。

### REV-02（P0）「清空全部数据」执行即失败，且已清空 `sources` 无法回滚

- **文件:行号**：`src/services/settingsService.ts:217-232`（`resetAllData`，第 222 行 `await sourceRepo.clear()`）、`src/db/repositories/sourceRepo.ts:74-78`
- **问题**：`resetAllData` 在 `withTx([...9 个 store], 'readwrite')` 回调第一行调用 `sourceRepo.clear()`。该方法**不接受 `tx`**（签名 `clear(): Promise<void>`），内部自开事务，导致外层事务在 `await` 期间自动提交；随后第 223 行 `mediaRepo.clear(tx)` 直接抛 `InvalidStateError`，`withTx` 捕获后转成 `E_DB`。
- **实测证据（CDP 探针，真实页面调用 `settingsService.resetAllData({keepDemo:true})`）**：
  ```json
  { "before": {"sources":1,"history":3,"media":12},
    "after":  {"sources":0,"history":3,"media":12},
    "error":  {"code":"E_DB","message":"本地数据读写失败，请重试"} }
  ```
  逐步探针确认失败点：`'sourceRepo.clear resolved'` → `'outer tx media clear THREW: InvalidStateError … transaction has finished'`。
- **影响**：设置页「清空全部数据」（`SettingsView.vue:159-179`）**必然失败**并 Toast 报错；更严重的是 `sources` 已被真实清空而 `media/history/favorites/downloads` 未动，应用进入"源全没了但缓存还在"的不一致状态，且 `keepDemo` 分支也不会执行（演示源不会补种）。属于数据安全级缺陷。
- **建议**：`sourceRepo.clear` 增加可选 `tx`（与其余 6 个 repo 对齐），`resetAllData` 传 `tx`；修复后补一条单测（当前 `resetAllData` 无任何测试覆盖）。
- **对应**：FR-41（清理）、FR-44/AC-99（清空保留演示源）、技术方案 API-10。

### REV-03（P1）Android 权限声明与实现不匹配，`allowBackup` 与"数据仅存本机"承诺冲突

- **文件:行号**：`android/app/src/main/AndroidManifest.xml:9-17`（权限）、`:24`（`android:allowBackup="true"`）
- **问题**：
  1. 声明 `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC`，但全仓无任何前台 Service 实现（`grep -rn "ForegroundService\|startForeground" src android` 无命中），下载/播放在后台一律暂停（符合首版 Q-03 取舍），这两条权限属冗余声明。
  2. 声明 `POST_NOTIFICATIONS`，但项目未使用 `@capacitor/local-notifications`，也无通知代码。
  3. 声明 `READ_MEDIA_VIDEO` / `READ_EXTERNAL_STORAGE`，但下载只写应用私有目录（`Directory.Data`），播放只走 `Capacitor.convertFileSrc()`，**从不读取用户相册/外部媒体**。
  4. `android:allowBackup="true"` 会让系统云备份（Google Drive / 厂商云）抓走 IndexedDB 内的源凭据与观看历史，与 SRS 6.5「源凭据仅存本机」「数据仅保存在本机，不上传服务器」的表述在外延上冲突。
- **影响**：AC-105 相邻的"权限最小化"要求不达标；应用商店审核/用户信任层面有风险；`READ_MEDIA_VIDEO` 属敏感权限，纯属"申请了但不用"。
- **建议**：删除 `FOREGROUND_SERVICE*`、`POST_NOTIFICATIONS`、`READ_MEDIA_VIDEO`、`READ_EXTERNAL_STORAGE` 四条声明（首版均不需要）；`allowBackup` 改 `false`，或保留但配 `android:fullBackupContent`/`dataExtractionRules` 排除 WebView 数据目录。改后重新 `npx cap sync android` + `assembleDebug` 回归。
- **对应**：SRS 6.5 安全与隐私；FR-33/AC-75（私有目录落盘）；Q-03。

### REV-04（P1）AC-60 错误码映射缺少单测，且 `E_NOT_FOUND` 文案与 AC 期望不一致

- **文件:行号**：`src/shared/errors.ts:20`（`E_HTTP_404: '资源不存在(404)'`）、`:26`（`E_NOT_FOUND: '内容不存在'`）；测试缺口：`tests/` 下无任何 `ERROR_MESSAGES` 断言
- **问题**：
  1. `src/shared/errors.ts:7` 注释写明「AC-60 单测直接断言该表」，但 `grep -rn "ERROR_MESSAGES" tests` 为 0 命中；AC-60 明确要求 `E_NOT_FOUND → "资源不存在(404)"`、`E_DRM_PROTECTED → "不支持受保护内容"`、`E_UNSUPPORTED_FORMAT → "暂不支持该格式"`、未知码 → "播放失败，请重试"。
  2. 实现里 `E_NOT_FOUND` 是「内容不存在」而非 AC-60 要求的「资源不存在(404)」；未知码回退是「操作失败，请重试」而非「播放失败，请重试」。文案与 AC 字面不一致（语义相近，但 AC 是"可被第三方按步骤复现判定"的口径）。
- **影响**：AC-60 无法判"通过"；错误文案在下游（`ErrorState`/`PlayerErrorPanel`）虽另有 code→建议映射，但断言基线缺失意味着后续改动无回归保护。
- **建议**：新增 `tests/unit/errors.spec.ts`，对 `ERROR_MESSAGES` 做全表快照式断言并覆盖 AC-60 四条指定映射；就 `E_NOT_FOUND`/未知码文案与需求方确认后二选一（改表 or 修改 AC 措辞，需走变更记录）。
- **对应**：FR-25 / AC-60；技术方案第 15 章（该表本身也未列 `E_NOT_FOUND`，属文档与 AC 的既有偏差）。

### REV-05（P1）`AC-55` 线路切换失败未"回退原线路"，当前实现会停留在失败线路上

- **文件:行号**：`src/views/PlayerView.vue:317-331`（`onSwitchLineById`）、`:305-315`（`onSwitchLine`）
- **问题**：两个切换入口都是**先改 `lineId.value` 再 `resolveAndLoad()`**。若目标线路 `resolvePlay` 失败，`loadError` 被设置、播放器中止，但 `lineId` 仍是失败线路；重试也仍在失败线路上。AC-55 要求「目标线路 resolve 失败时回退到原线路并提示"切换失败，已保持原线路"，播放不中断」。
- **影响**：用户在多线路场景下点到坏线路后无法自动恢复，只能手动再切回（且错误面板的"切换线路"会切到另一条，可能又失败）。
- **建议**：切换前保存 `previousLineId`；`resolveAndLoad` 失败时回滚 `lineId` 与路由 query，重新加载原线路并 Toast「切换失败，已保持原线路」。
- **对应**：FR-23 / AC-55。

### REV-06（P1）播放器网络错误自动重试使用裸 `setTimeout`，页面销毁后仍可能触发

- **文件:行号**：`src/player/PlayerController.ts:277-295`（`handleEngineError`，第 281 行 `setTimeout(...)`）
- **问题**：`handleEngineError` 在网络错误时 `setTimeout(..., NETWORK_RETRY_DELAY_MS)` 延迟重载，但该定时器**未登记、`destroy()` 中未 `clearTimeout`**（`destroy()` 只清了 `hideTimer`）。虽回调内用 `this.destroyed` 兜底提前 return，但定时器本身仍持有闭包 1s；更关键的是若用户在 1s 内切集（`load()` 重新进入，`destroyed` 仍为 false），旧重试会与新的 `attachEngine` 竞争，产生双引擎加载。
- **影响**：AC-58（自动重试 1 次）在快速切集场景下可能出现"重试把用户刚切的集顶掉"或引擎重复 attach；属于可复现的竞态（时序相关）。
- **建议**：把重试定时器记为 `private retryTimer`，`destroy()` 与 `load()` 入口均 `clearTimeout`；或用 `AbortController` 统一取消。
- **对应**：FR-25 / AC-58；NFR-P07（退出播放页释放实例）。

### REV-07（P1）`WEB_MAX_BYTES` 注释与实现不一致，Web 端 1GB 前置提示未接线

- **文件:行号**：`src/services/downloadSink.ts:103-104`（注释写「超过 512MB 直接抛配额错误」，常量实为 `2 * 1024 * 1024 * 1024`）、`:128`；`src/services/downloadService.ts:469-471`（`needsAppForLargeFile` 无任何调用方）
- **问题**：SRS FR-33 要求「单文件 >1GB 时提示"浏览器环境建议改用 App 下载"」，`downloadService` 已实现 `needsAppForLargeFile()`（阈值 `DOWNLOAD_WEB_SIZE_WARN_BYTES = 1GB`），但 `grep` 显示 **UI 无调用**。同时 sink 层的硬上限是 2GB（且注释说 512MB），三层阈值（1GB 提示 / 2GB 硬失败 / 注释 512MB）互相矛盾。
- **影响**：AC-76「单文件 1.2GB 时前置提示使用 App 下载」未实现（不会提示，会一直下到 2GB 才抛 `E_STORAGE_QUOTA`）；Web 端大文件会先吃掉内存再失败。
- **建议**：在 `DetailView.downloadEpisodes` / `EpisodePickerSheet` 提交前调用 `needsAppForLargeFile`（`totalBytes` 已知时）或按 `Content-Length` 预检；统一三处阈值为 1GB（提示）/ 1GB（硬拒）并修正注释。
- **对应**：FR-33 / AC-76。
