## 1. 一页结论

- **核心矛盾**：内置推荐订阅声明的采集源里 **约 77% 是 jar/drpy 爬虫源**（14 条可解析 JSON 订阅共约 1077 个源条目，其中 `csp_` 爬虫约 830 个、HTTP 站点约 138 个）。爬虫源恰恰是**冷启动最慢（35~75s）、最易超时、最易崩溃**的类型；而搜索扇出按"并发 8 / 全局 28s / 爬虫单源 20s"调度——**调度模型与源构成严重错配**。
- **最严重的两个问题都是"静默失败"**：
  1. **P0-A 单源预算超时被当成"用户取消"吞掉**：爬虫源 20s 预算到期 → `AbortController.abort()` → 原生竞速抛 `E_ABORTED` → `isCanceled()` 静默 return。结果：**失败面板少计、超时退避永不触发、空态显示"换个关键词"误导用户**。这与 `searchBudget.ts` 自己声明的契约（"该源计入失败列表"）直接矛盾。
  2. **P0-B 全局 28s 截止静默丢弃未启动源**：上百源的订阅，并发 8 × 28s 实际只能搜约 8~16 个源，其余**既不搜索、也不计失败、进度条永远到不了 total**。叠加 P0-A，即使所有源都超时，`failed.length=0 ≠ enabled.length` → 不抛错 → 返回空结果 + 零诊断。
- **问题分级汇总**：P0 **2** 项、P1 **5** 项、P2 **5** 项，共 **12** 项。
- **Top 3（先做）**
  1. **P0-A**：区分"预算超时"与"用户取消"，让爬虫超时可见、可重试、可退避（一处标志位 + 一处错误码即可根治，收益最大）。
  2. **P0-B**：全局截止丢弃的源要计入"未搜索"诊断，进度与空态文案如实披露"仅搜索了 N/M 个源"。
  3. **P1-A**：`SEARCH_FAILURE_LABELS` 缺 3 个分类键，失败面板会渲染出 "N undefined"，且是被 `vite build` 掩盖的潜伏 TS 错误。
- **一句话结论**：搜索主链路"能跑通"，但在推荐订阅这种**爬虫源占八成、单订阅上百源**的真实场景下，**大量源被静默跳过且用户毫不知情**——当前最大风险不是"搜不到"，而是"**搜不全却假装搜全了**"。

```

                 ├─ 本地缓存 searchByTitle（毫秒级）

                 │     searchCandidate：跳过 unreachable/bad_config/auth_failed + ext.searchable===false

                 │     while cursor<enabled.length：
                 │        signal.aborted → return
```

## 5. 分级问题清单

> 每项含：现象 / 根因 / 证据 / 影响 / 建议。证据行号基于基线 `a65c986`。

### P0-A 单源预算超时被静默吞掉（爬虫超时不可见、退避失效、空态误导）

- **现象**：用饭太硬/潇洒这类爬虫订阅搜索热门片名，大量源 20s 到期后**失败面板一个都不显示**，结果区直接"没有找到相关内容 / 换个关键词，或检查源是否启用"；同一批慢源下一轮搜索照样重打，从不退避。
- **根因**：预算到期与用户取消走了同一条错误码。
  - `libraryService.ts:396` `const timer = setTimeout(() => controller.abort(), budgetMs)` —— **没有 `timedOut` 标志**，到期 abort 与用户 abort 无法区分。
  - `SpiderAdapter.ts:294` `onAbort = () => fail(new AppError('E_ABORTED'))` —— 外部 abort 一律 `E_ABORTED`。
  - `SpiderAdapter.ts:678/684` 搜索 invoke 的 `raceNative` 超时是 `NATIVE_INVOKE_TIMEOUT_MS=30s`，**大于**爬虫单源预算 20s → 20s 时预算 abort 先到 → 永远走 `E_ABORTED`，原生 30s 的 `E_TIMEOUT` 分支对搜索是死代码。
  - `libraryService.ts:668-669` catch 里 `done += 1; if (isCanceled(e)) return;` —— `E_ABORTED` 被静默丢弃，**不进 `failed`、不回调 `onPartial(error)`**。
  - `errors.ts:167-168` `isCanceled` 把 `E_ABORTED/E_CANCELED` 都算取消。
  - `libraryStore.ts:535` `recordTimeoutStreak` 只对 `E_TIMEOUT` 累加 → 爬虫搜索超时**永远凑不满 3 次退避**。
- **契约矛盾**：`searchBudget.ts:9-10` 明文声明"超时语义不变（仍是 AbortController 中止 **+ 该源计入失败列表**，可只重试失败源）"。实现与契约相反。
- **影响**：推荐订阅 77% 是爬虫源，这正是它们超时时的统一归宿——**搜索失败被系统性掩盖**。用户看不到"哪些源超时、该换源还是该等"，失败面板/只重试失败源/退避三个机制对爬虫全部失效。
- **建议**：在 `searchOneSource` 加 `let timedOut=false`，timer 回调里 `timedOut=true; controller.abort()`；catch 中 `if (timedOut) throw new AppError('E_TIMEOUT', …)`，仅当 `!timedOut && isCanceled(e)` 才静默。一处标志位即可让爬虫超时计入 failed、触发退避、可重试，且与既有契约对齐。

### P0-B 全局 28s 截止静默丢弃未启动源（搜不全却假装搜全）

- **现象**：导入潇洒（112 源）/心魔（151 源）后搜索，进度条停在例如"12/112"后消失，结果只有寥寥几条；用户以为"搜完了就这些"，实际 100 个源根本没启动。
- **根因**：
  - `libraryService.ts:686` worker 循环里 `Date.now()-start > 28000 → return`，**剩余源直接不启动**，既不进 `remoteResults` 也不进 `failed`，`done` 永远 < `total`。
  - 并发 8 × 28s，若爬虫单源贴近 20s，一轮实际只能完成约 8~16 源；上百源订阅的覆盖率 < 15%。
  - `libraryService.ts:715` 抛错条件是 `merged 空 && failed.length===enabled.length`。叠加 P0-A（超时不进 failed），即使**所有启动的源都超时**，`failed.length=0 ≠ enabled.length` → **不抛错**，返回 `items:[], candidates:112, filteredOut:0, failed:[]`。
  - `SearchView.vue:104-110` `zeroCandidates` 只在 `candidates===0 && filteredOut>0` 时给诊断；上面这种 `candidates=112` 的情况**不触发任何诊断**，空态文案退化为"换个关键词"。
  - `SearchView.vue:679-686` 进度"仍在搜索其它源（done/total）"仅在 `isSearching` 时显示，search 一 resolve 就消失，**用户永远看不到"只搜了 N/M"**。
- **影响**：这是推荐订阅场景下**最普遍的体验黑洞**——源越多搜得越不全，且 UI 完全不披露。与 P0-A 叠加后，"全超时"会伪装成"没搜到"。
- **建议**：① 截止后把未启动源记入 `skipped`（新字段）并在空态/结果区披露"因超时仅搜索 N/M 个源，可重试剩余"；② 提供"继续搜索剩余源"动作（复用 `retryFailedSources` 的增量合并思路）；③ 进度条结束后保留终态摘要而非直接消失；④ 重新评估并发/截止与爬虫预算的配比（见 §6）。

### P1-A 失败分类标签缺 3 键 → 渲染 "N undefined" + 潜伏 TS 错误

- **现象**：失败面板遇到安全模式/隔离/类名不匹配三类源时，汇总文案出现"2 undefined"。
- **根因**：`searchAggregate.ts:251-259` `SEARCH_FAILURE_LABELS: Record<SourceFailureKind,string>` 只写了 7 个键；而 `sourceFailure.ts:17-27` `SourceFailureKind` 有 **10** 个变体（多出 `safe_mode`/`quarantined`/`spider_mismatch`）。`searchAggregate.ts:295` `label: SEARCH_FAILURE_LABELS[kind]` 对这三类取到 `undefined`，`:318` 拼成 `${count} ${label}` → "N undefined"。
- **门禁掩盖**：这是 `Record<Union,…>` 缺键的**编译期错误**，但 `npx vite build` 不做类型检查（见 memory / 2026-11-06 体检"门禁变红"），错误被带上线。
- **建议**：补齐 3 个键（文案可直接复用 `sourceFailure.ts` 的 `SAFE_MODE_MESSAGE` 等常量）；并把 `npm run typecheck` 纳入构建门禁，避免同类潜伏错误。

### P1-B 搜索预算档位不传导到采集管道（站点源 patient 档无效）

- **现象**：设置里把搜索预算调到"耐心"，站点源搜索并没有变宽松；调到"快速"反而让更多站点源静默失败。
- **根因**：档位只缩放 `libraryService.ts:395` 的**外部** `budgetMs`，而站点源真正干活的是采集管道 `scheduler.ts:55` `DEFAULT_BUDGET_MS.search=8000`（**固定**，不读档位）。
  - patient：外部 8s×1.5=12s，但管道内部 8s 就放弃 → 有效预算仍是 8s，**档位无效**。
  - fast：外部 8s×0.6=4.8s < 内部 8s → 4.8s 外部 abort → `E_ABORTED` → 被 P0-A 吞掉，**站点源静默失败**。
- **建议**：把档位倍率透传到 `scheduler` 的 search 意图预算（调用方显式传 `budgetMs`），让内外预算一致；或明确"档位只作用于爬虫源"并在设置文案标注。

### P1-C 爬虫冷启动 > 搜索预算 → 首搜必丢、预热覆盖不足

- **现象**：刚导入订阅第一次搜索，爬虫源几乎全军覆没；第二次稍好。
- **根因**：
  - `SpiderAdapter.ts:261` jar 加载超时 `NATIVE_LOAD_TIMEOUT_MS=75s`；`:665` `invoke` 内 `ensureLoaded(source, signal)` 冷启动可达 35~75s，**远超 20s 搜索预算** → 首次必被预算 abort（再被 P0-A 吞掉）。
  - `libraryService.ts:392` `prewarm` 是 fire-and-forget，与搜索并发，无法保证搜索开始前 jar 已热。
  - `sourceStore.ts:207-238` `warmupSpiderSources` 只预热 **top 5**、并发 2 —— 面对单订阅上百爬虫源，预热覆盖率极低。
- **建议**：① 导入完成后后台分批预热爬虫 jar（按健康/延迟排序，超出 top5）；② 搜索时对"冷源"给一次性更宽预算或明确标记"冷启动中"而非静默丢弃；③ 与 P0-A 联动，让冷启动超时可见、可重试。

### P1-D 订阅字段 ext.timeout / quickSearch / playerType 解析入库却无人消费（死配置）

- **现象**：订阅里声明的 `timeout`、`quickSearch`、`playerType` 被解析进 `ext`，但搜索/播放行为不受其影响。
- **根因**：`subscriptionParser.ts:416-456` 把这三个字段合入 `ext`；但在 `src/sources` 全量 grep `quickSearch|ext.timeout|playerType` **零命中**——没有任何适配器读取它们。
- **影响**：订阅作者/用户预期落空；`quickSearch`（TVBox 的快速搜索标记）本可用于搜索候选优先级，`timeout` 本可覆盖单源预算，现在都是死字段。
- **建议**：要么消费（`ext.timeout` 覆盖单源预算、`quickSearch` 提升候选优先级），要么停止解析入库以免误导；优先消费 `timeout`，与 P1-B 的预算传导一并设计。

### P1-E 站点源空结果触发双请求，吃掉 8s 预算

- **现象**：慢网下站点源搜索经常超时，尤其是老版 CMS。
- **根因**：`SiteAdapter.ts:411-418` 先 `send('detail')`，列表为空再 `send('videolist')` —— **两次串行往返**都在同一个 8s 预算内。首次请求耗满预算时，回退请求没时间跑。
- **建议**：搜索意图直接走 `ac=videolist`（TVBox 搜索约定），跳过 `detail` 首请求；或把回退改为并行竞速而非串行。

### P2-A "选定源"范围有逻辑无 UI 入口（不可达功能）

- **根因**：`libraryStore.ts:555-556` `scopeSourceIds` 支持 `searchScope==='selected'` 取 `searchSelectedSourceIds`；`setSearchScope(scope, selectedIds)` 也接受选定 id。但 `SearchView.vue:259-264` `scopeOptions` 只有 all/site/spider/douban，**没有 selected**，也没有任何勾选源的 UI。
- **影响**：用户无法"只搜我指定的几个源"——而这恰恰是上百源订阅下最实用的降噪手段（与 P0-B 强相关）。
- **建议**：补"选定源"范围 chip + 源多选弹层；或暂时移除 store 里的死分支以免误导后续维护。

### P2-B "仅看可播"只预检前 12 条 → 开关后结果骤减甚至翻空

- **根因**：`libraryStore.ts:102` 可播性预检只 `items.slice(0,12)`；`:84-88` `searchPlayableOnly` 过滤掉"代表未确认可播"的组；`:465` `searchState` 由过滤后的 `searchResults.length` 判定。第 13 条之后的组没有可播性数据（status=unknown）→ 开启开关后被全部过滤 → 结果骤减，极端情况 `searchState` 翻成 `'empty'`。
- **影响**：用户开"仅看可播"想降噪，却看到结果几乎清空，误以为没有可播内容。
- **建议**：① 开关开启时按需扩大预检范围（至少覆盖当前可见组）；② 文案区分"未检测"与"不可播"，未检测组不应被直接过滤；③ `searchState` 判定与 playableOnly 解耦，避免误翻空态。

### P2-C 搜索建议纯本地静态，输入即触发全量远程扇出

- **根因**：`suggestService.ts:24-35` 热门词是写死的 `HOT_SEARCH_LIST`，建议只来自本地历史/缓存；`SearchView.vue:129-139` 每次 keyword 变化（300ms 防抖后）都 `runSearch` 全量扇出。
- **影响**：中文 IME 整词上屏尚好，但分次输入/改词时，每个中间词都打一次上百源的远程扇出（旧请求被 abort，但爬虫冷启动已在原生线程池跑起来，浪费且加剧 P0-B）。没有廉价的远程联想兜底。
- **建议**：① 输入阶段只做本地建议，**回车/提交才远程扇出**（或 ≥2 字符且停顿更久才搜）；② 中间态用本地缓存命中先上屏；③ 远程联想可作为可选增强。

### P2-D 直播/多仓/加密源混入搜索候选，无能力分级

- **根因**：`libraryService.ts:419-430` `searchCandidate` 只按 health 与 `ext.searchable` 过滤，**不区分源能力类型**。推荐清单里 Guovin/YueChan（m3u 直播）、戏曲音乐（hex）、游魂（HTML 多仓）可达但对片名搜索无贡献；多仓展开后进一步放大候选规模。
- **影响**：无效候选占用并发槽与预算，加剧本就紧张的 28s 覆盖率（P0-B）；直播源参与 VOD 搜索只会返回空或异常。
- **建议**：① 导入时按正文类型打能力标签（vod/live/multi/encrypted），搜索候选默认排除 live/未展开 multi；② 清单层面对死链（§3.2 第 1 条）做一轮清理与"最近验证时间"披露。

### P2-E 推荐清单冗余与死链（清单治理）

- **根因/证据**：§3.1 实测 6 条死链/不可达；王二小≡牛二逐字节相同（`importService.ts:197-204` 按 key 去重后第二条零增量）。
- **建议**：① 清理 4×404 + 欧歌 + 巧技，或替换为可达镜像；② 牛二保留为"备用镜像"但在导入预览明示"与王二小完全重复，导入不增加新源"；③ 给推荐条目加"最近可达性验证时间"，定期回归。

### 6.1 调度配比重估（针对爬虫占八成的源构成）

当前"并发 8 / 全局 28s / 爬虫 20s"在单订阅上百爬虫源时覆盖率 < 15%。可考虑（需真机验证后定参）：
- **分层调度**：先用本地缓存 + 站点源（快）秒级上屏，爬虫源后台渐进补充（已有 onPartial 基础）。
- **健康/延迟优先**：候选按 `healthTier + latency` 排序后再扇出（`libraryService.ts:600-614` 已有同源排序逻辑可复用），让好源先搜、慢源后置。
- **覆盖率披露优先于提速**：哪怕维持 28s，也要如实告诉用户"搜了 N/M、剩余可继续"，把"静默丢弃"变成"显式可继续"。
