### 2.2 FIX-03 播放侧：supersedePreflight / AbortController / epoch 竞态

**结论：不通过。**

**做对的部分（确认无缺陷）：**

1. 代次与取消：`attachEngine` 每次先 `supersedePreflight()` 再区分引擎（`PlayerController.ts:254`），`supersedePreflight` 先递增代次再 abort（L406-411）。
2. 旧结果写回：`runManifestPreflight` 在 `await` 之后才校验 `epoch !== this.preflightEpoch`（L428），旧结果不可能污染新播放。
3. 回调竞态：`finally` 用 `if (this.preflightAbort === controller)`（L430-432）避免旧的 finally 清掉新句柄。
4. 销毁：`destroy()` 调用 `supersedePreflight()`（L884），在 `this.destroyed = true` 之后。
5. 网络抖动不误判：`preflightManifest` 任何失败返回 `null`（`src/player/sourceGuard.ts:117-170`），`detectUnsupportedSource` 只在拿到文本时判 DRM（L70-87）。

**缺陷 1（P1，REV-27）：播放侧只扫描顶层清单，master→variant 的 DRM 漏检。**

- `runManifestPreflight` 只 `preflightManifest(playback.url)`（L421-427），而 `preflightManifest` 只 GET 一个地址（`sourceGuard.ts:117-170`）。下载侧做了两级（L409/L431），播放侧只有一级。
- 实测（一次性探针，已删除）：源为 master 清单（master 内无 KEY），变体 `720p.m3u8` 含 `#EXT-X-KEY:METHOD=SAMPLE-AES`。结果：

```text
[PROBE-MASTER] {"code":"E_UNSUPPORTED_FORMAT","message":"当前环境不支持 HLS 播放","fetched":["https://a.com/master.m3u8"]}
```

  只请求了 master，未请求变体；真机上等价于交给 hls.js 后失败（`E_DECODE`，文案「视频解码失败」），且 `E_DECODE` 在 `FAILOVER_ERROR_CODES` 内（`PlayerView.vue:666-674`），会触发自动换线/换源的连锁失败。
- 与 AC-40「传入 … 带 `#EXT-X-KEY:METHOD=SAMPLE-AES` 的流时，提示…受保护内容，不尝试绕过」直接冲突；多码率（master）是常见形态，不是边角输入。

**缺陷 2（P1，REV-28）：`E_ABORTED` 被包装成用户可见错误，切集是必现路径。**

- `PlayerController.load()` 对 `E_ABORTED` 直接 `throw e`（L227），意图是「由 `load()` 静默处理」——但控制器外层的 `usePlayerController.load()` 没有任何取消判断：

```ts
// src/composables/usePlayerController.ts:305-310
try {
  await c.load(opts);
  await c.play();
} catch (e) {
  player.patch({ error: toErrorShape(e), loading: false, playing: false });
}
```

  `E_ABORTED` 的 `AppError` 在 L428 携带消息「播放已切换，本次预检作废」，于是 `player.error` 变为 `{code:'E_ABORTED', message:'播放已切换，本次预检作废'}`。
- 触发路径不是极端并发：`PlayerView.chooseEpisode()` 先 `router.replace(...)` 再 **`void resolveAndLoad()`**（`PlayerView.vue:972-980`），而 `watch(episodeIdParam)` 在路由变化后**又**执行一次 `resolveAndLoad()`（L1115-1122）——一次普通切集即产生两路并发加载；后一路的 `supersedePreflight` 让前一路抛 `E_ABORTED`。
- 可见后果：`player.error` 在「后一次 load 的 `error:null` 初始 patch 之后」被写入，且**没有任何成功路径会清空 `player.error`**（`usePlayerController.ts` 全文仅在 L297/L309 写该字段）；`PlayerView.vue:1275/1348` 用 `v-if="player.error"` 挡住播放画面并渲染错误面板 → 新一集已在播，却被「播放已切换，本次预检作废」的遮罩盖住。
- 与自测记录冲突：`docs/08` §1 第 4 行称「被取代时抛 `E_ABORTED` 且不覆盖状态、不误报错误」，该声明只在 `PlayerController` 内部成立，端到端不成立。
- 现成修复基元已存在：`src/shared/errors.ts:166-169` 的 `isCanceled(e)` 就是为此定义的。

**其余确认项：**

- 被取代的一路会让控制器 `state` 停留在 `loading`（catch 中在 `setState('error')` 之前返回）；若有更新的加载，新加载会覆盖；若因 `destroy()` 被取代，页面正在卸载，无用户可见影响。可在 REV-28 修复时一并置 `idle`（非必须）。

### 2.3 FIX-04：回退条件是否过宽、token 还原是否引入越权、签名 URL 是否被破坏

**结论：有条件通过。**

| 关注点 | 结论 | 证据 |
| --- | --- | --- |
| 回退条件过宽 | **是（P2）**：`!response.ok` 即回退，401/403/404/416 全部回退直连（`hlsDownloader.ts:674-687`） | 4xx 大概率直连同样失败，只会多一次请求；若上游是「代理 302 跟随成功但最终 403、直连却因 UA 不同成功」则回退有意义。建议只在异常/超时/5xx 回退，4xx 直接按原状态报错，避免掩盖 401/403 的真实原因 |
| token 重编码注入/越权 | **无新增越权** | `unwrapProxiedUrl` 仅接受「同 host + `/p/` + 非空 token」的回环地址（L274-290），解码结果必须是 `http(s)`；解析出的上游地址随后由 `resourceUrl()` 用**本任务 token** 重新编码。恶意清单本来就能把分片指向任意主机并让代理带上任务头，unwrap 没有扩大这一既有信任模型 |
| 签名绝对 URL | **未被破坏** | 还原的是代理 `URLEncoder.encode` 前的原始串（`+`→空格后再 `decodeURIComponent`，L284-285），重新编码由代理 `URLDecoder` 对称还原；`%` 序列经双重编码/解码后回到原值 |
| 302 base | **已修正** | `LocalProxyPlugin.java:272` 由 `target.url` 改为最终 `url`；重写条件 `url` 或 `target.url` 任一含 `.m3u8`（L238） |
| 取消语义 | **正确** | `fetchManifestText` 入口与 catch 内都判 `signal.aborted` 抛 `E_ABORTED`（L673、L684） |
| 副作用 | 代理路径不重复发头（头由 token 侧注入），直连路径才带 `headers`（L688-693） | 无双重头 |
