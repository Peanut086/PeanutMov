## 1. 版本统一（单一来源 = `package.json#version`）

### 1.1 改动前的事实

| 位置 | 改动前 | 性质 |
| --- | --- | --- |
| `package.json:4` | `"version": "0.1.0"` | 前端 `__APP_VERSION__` 的来源（设置页/关于页展示） |
| `android/app/build.gradle:10-11` | `versionName "1.0"`、`versionCode 1` | 硬编码，与前端不同源 |
| `android/variables.gradle:2` | `minSdkVersion = 23` | 与 SRS NFR-C01 不一致 |

### 1.2 改动后

`android/app/build.gradle:25` 起 `resolveVersion()` 在配置阶段解析仓库根 `package.json`，`android/app/build.gradle:100-101` 将其写入 `defaultConfig.versionCode/versionName`；全仓库不再存在第二处可手改的版本号。

派生规则（唯一权威说明，写在 `android/app/build.gradle:3-16` 与 SRS §6.2）：

```
versionName = semver 核心 x.y.z（丢弃 v 前缀 / -prerelease / +build 元数据）
versionCode = x * 10000 + y * 100 + z            // 0.1.0 → 100
约束：minor ≤ 99、patch ≤ 99（满 100 必须进位）、major ≤ 199（Android 上限 2100000000）
```

### 1.3 本次修复的 3 个缺陷（`resolveVersion()` 正确性核对结论）

| # | 原实现问题 | 触发条件 | 后果 | 现状 |
| --- | --- | --- | --- | --- |
| 1 | 未剥离 `v` 前缀，`"v1.2.3"` 被解析为 `["v1",2,3]` → `"v1".isInteger()==false` → 0 | `package.json` 写成 `v1.2.3` | **静默**产出 `versionName=0.2.3 / versionCode=203`，构建不报错，版本号与预期完全不符 | 已修：剥离 `v/V` 前缀 |
| 2 | 先按 `-` 切分但未处理 `+build` 元数据 | `"0.1.0+5"` → 第三段 `"0+5"` 非整数 → 0 | 静默降级为 `0.1.0/100`，无任何提示 | 已修：`-` 与 `+` 双向切分，并打印 INFO 说明仅取核心版本 |
| 3 | `versionCode` 编码越界无提示 | `minor`/`patch` ≥ 100（如 `0.1.100`） | 与相邻版本碰撞（`0.1.100` 与 `0.2.0` 同为 200），覆盖安装/上架被拒，且现场无日志可查 | 已修：越界打印 WARN 并提示先升 major/minor；编码上限写入注释与 SRS |

补充加固：

- 版本字符串 `trim()`、非数字段直接判无效回退（原实现把非数字段当 0，`"1.0.abc"` 会被静默当成 `1.0.0`）。
- 段数 > 3（非标准 semver 如 `1.2.3.4`）打印 WARN 后取前三段。
- 每次配置阶段打印一行 `VERSION: versionName=... versionCode=... (source=../package.json '...')`，用于解决"升级/问题定位困难"（原实现只在回退时打印 WARN，正常路径无任何版本输出）。

## 2. minSdk 决策（23 → 29）

### 2.1 扫描方法

- 全量扫描 `android/app/src/main/java` 的 23 个 Java 文件 + `AndroidManifest.xml` + `variables.gradle`：`grep -rn "SDK_INT|VERSION_CODES"`。
- 全量扫描存储访问面：`getExternalStorageDirectory|MANAGE_EXTERNAL_STORAGE|WRITE_EXTERNAL_STORAGE|requestPermissions|getFilesDir|MediaStore`。
- 依赖侧：Capacitor 7 官方最低要求 API 23（其 `@capacitor/android/capacitor/build.gradle:47` 同样读取 `rootProject.ext.minSdkVersion`，不写死）；抽查 `wrapper-android-3.2.3.aar` 的 `minSdkVersion="21"`，media3 1.3.1 / okhttp 4.9.3 / jsoup 更低。**没有任何依赖把下限抬到 29 以上**（依据：合并清单成功、`assembleDebug` 通过——库的 minSdk 高于 app 时清单合聚会直接报错），也**没有任何依赖要求 23–28 才可用**。

### 2.2 `Build.VERSION.SDK_INT` 分支清单（是否存在 API 23–28 专有逻辑）

| 文件:行 | 分支 | 抬到 29 后 | 判定 |
| --- | --- | --- | --- |
| `download/DownloadService.java:76` | `>= O`（通知渠道） | 恒真，成为无分支直路 | 死代码，无害 |
| `download/DownloadService.java:93` | `>= UPSIDE_DOWN_CAKE`（前台服务类型） | 仍需 34+ 判定 | 保留 |
| `download/DownloadService.java:134` | `>= M`（`FLAG_IMMUTABLE`） | 恒真 | 死代码，无害 |
| `download/DownloadService.java:169` | `>= O`（`startForegroundService`） | 恒真 | 死代码，无害 |
| `DownloadPlugin.java:191` | `>= O`（通知渠道） | 恒真 | 死代码，无害 |
| `ExoPlayerPlugin.java:450` | `>= O` | 恒真 | 死代码，无害 |
| `NetdiskPlugin.java:45,62` | `>= R`（`isExternalStorageManager` / 跳转设置页） | 29 走 else 分支，30+ 走 if 分支 | **必须保留**（见 §2.4） |
| `PlayerUiPlugin.java:44,58` | `>= P`（刘海 `cutoutMode`） | 恒真 | 死代码，无害 |

结论：**没有任何 API 23–28 专有逻辑**。抬到 29 只是让 `O`/`P`/`M` 三类分支恒真，不影响行为；本次不删除这些分支（避免无谓 diff，且回退 minSdk 时仍可用）。

### 2.3 存储访问面清单（决定 23–28 能否安全放弃）

| 用途 | 路径 | 抬到 29 后 |
| --- | --- | --- |
| 下载文件、drpy 规则、爬虫 jar/dex、爬虫日志、投屏临时文件、网盘 cookie 备份 | `context.getFilesDir()` 应用私有目录（`RangeDownloader.java:555`、`CatvodLoader.java:534`、`DrpyRuntime.java:97`、`SpiderPlugin.java:900/1029/1652/1760`、`SpiderLogStore.java:86`、`NetdiskPlugin.java:259/301`、`CastSharePlugin.java:52`） | 不受影响，任意 API 均可用 |
| 网盘账号 cookie（TVBox jar 约定路径） | `Environment.getExternalStorageDirectory()/TVBox`（`NetdiskPlugin.java:356`、`NetdiskLoginActivity.java:375`） | 依赖 29 的 `requestLegacyExternalStorage` 或 30+ 的 `MANAGE_EXTERNAL_STORAGE`，**本来就与 23–28 无关** |

结论：没有"只有 API 23–28 才成立"的存储假设（例如 `MediaStore` 旧列名、`getExternalStoragePublicDirectory` 直写、`WRITE_EXTERNAL_STORAGE` 直授权路径均不存在）；因此抬 minSdk **不会破坏 API 23–28 的兼容代码**——因为根本没有这类代码。

### 2.4 决策与影响

**决策：`minSdkVersion = 29`（Android 10），与 SRS §1.4 / NFR-C01 对齐。**

理由：

1. 代码无 23–28 专有逻辑，保留 23 的收益仅是"能装"，代价是"能装但从未验证"（DEV-02 AND-02 已记录该预期偏差）。
2. SRS 的回归基线本身就是 Android 10 + Android 14 两台真机（AC-53、测试用例 §环境准备），23–28 不在任何验收路径上。
3. 29 是原生层存储分支的真实分界点（`requestLegacyExternalStorage` 仅 29 生效、`MANAGE_EXTERNAL_STORAGE` 仅 30+ 生效），把下限对齐到语义分界点，避免"路径从未被执行却被声明支持"。

影响：

- 安装面收窄到 Android 10 及以上；API 23–28 设备后续安装会被系统拒绝（这是本次决策的显式结果，已写入 SRS）。
- `AndroidManifest.xml` 的 `WRITE_EXTERNAL_STORAGE android:maxSdkVersion="28"` 在 minSdk 29 下成为永不生效的声明（无害，但建议随 AND-05 一并处理）。
- `android/capacitor-cordova-android-plugins/build.gradle:22` 的 `minSdkVersion ... : 23` 只是插件工程的兜底默认值，合并清单实测仍取 `app` 的 29（见 §1.5），无需改动。

### 2.5 本轮无法闭环的关联缺陷（AND-05 升级为阻塞项）

`AndroidManifest.xml` 中 `WRITE_EXTERNAL_STORAGE` 带 `android:maxSdkVersion="28"`，而 `NetdiskPlugin.hasAllFilesAccess()` 在 `SDK_INT < R` 时正是检查该权限（`NetdiskPlugin.java:49`），`requestAllFilesAccess()` 在 `SDK_INT < R` 时直接 resolve 不申请（`NetdiskPlugin.java:72-75`）。

后果：在 **API 29（Android 10）** 上，`WRITE_EXTERNAL_STORAGE` 不会被授予 → `/sdcard/TVBox` 不可写 → 网盘 cookie 推送必然失败。该缺陷在 minSdk 23 时存在于 23–29 全区间（DEV-02 AND-05 已记录为 P2）；抬到 29 后受影响的只剩 29 这一个 API 级别，但它恰好是新下限，即"最低支持设备上该功能不可用"。

修复须改 `AndroidManifest.xml`（`maxSdkVersion="29"` 或去掉该属性），**不在本任务允许的改动范围内**，已上报协调者（§5 第 1 条）。在修复前，Android 10 设备的"网盘登录 / cookie 推送"不应被当作可用能力对外声明。

## 5. 上报协调者的事项（需决策或超出本任务改动范围）

1. **【阻塞项，需扩范围】AND-05 与 minSdk=29 同批修复**：`AndroidManifest.xml` 的 `WRITE_EXTERNAL_STORAGE` 带 `maxSdkVersion="28"`，导致 API 29（新最低版本）无法写 `/sdcard/TVBox`，网盘 cookie 推送在 Android 10 上必然失败。建议一处改动：`maxSdkVersion="28"` → `"29"`（或去掉），或在 `requestAllFilesAccess()` 的 `< R` 分支补 `requestPermissions`。Manifest 不在本任务允许的改动文件内，需授权。
2. **【前端侧，需转派】`vite.config.ts:13` 的 `__APP_VERSION__` 取 `process.env.npm_package_version`**：只有经 `npm run build`（npm 注入环境变量）构建才等于 `package.json` 版本；直接 `npx vite build`、CI 直调 vite 或 `vite build --mode` 场景会得到 `0.0.0`，与 APK 的 `0.1.0` 再次分叉（`constants.ts:14` 只在空串时回退"未知版本"，防不住 `"0.0.0"`）。建议前端改为在 `vite.config.ts` 里直接读 `package.json`。本任务约束禁止改 `src/**` 与 `vite.config.ts`。
3. **【口径确认】`versionCode` 编码上限**：本次保留 `x*10000 + y*100 + z`（沿用 DEV-02 已验证的 `0.1.0 → 100`），代价是 `minor/patch` 达到 100 时必须进位，否则与相邻版本碰撞。个人项目实际不会触发；若后续要支持三位 patch，需要一次性的编码规则变更（会改变 `versionCode` 数值），请产品确认后再动。
4. **【文档顺带项】** `docs/01-需求/功能体检报告-2026-11-06.md`（OPT-06 行、REF-05 行）与 `docs/01-需求/决策记录-2026-11-06.md:112` 仍描述旧口径（"API 23 可安装 / 29 基线"）。这两份是时点性记录、且不在本任务允许的改动范围内，未修改；如需把体检报告标注为"已修复"请由文档负责人处理。

- 未做真机验证（无可用设备）：minSdk=29 的安装与运行只在构建产物层面验证（`minSdkVersion:'29'`），Android 10 实机冒烟需并入 AC-53 回归。
- 未运行 `lint`（`assembleDebug` 不触达 `lintVital`）：minSdk 抬升后可能出现"低版本兼容"类 lint 提示（如 `NewApi` 死分支告警），不影响构建；如发布流程要求 lint 零告警，需另立任务处理。
- 未验证 `versionCode` 单调性在真实覆盖安装上的效果（需两台设备或卸载重装链路），当前仅保证公式随 semver 单调。
- `resolveVersion()` 仍在配置阶段读取文件，未启用 Gradle 配置缓存（未配置 `org.gradle.configuration-cache`）；若后续开启，需给文件读取加 `providers.fileContents()` 适配。
