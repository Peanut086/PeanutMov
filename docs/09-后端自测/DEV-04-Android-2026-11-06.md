### 1.1 AND-14（P0 潜在）：移除原生 HLS 下载路径

**改动文件**

| 文件 | 改动 |
| --- | --- |
| `android/app/src/main/java/com/qoder/cinema/download/HlsDownloader.java` | **整文件删除**（329 行）。该类只被 `NativeDownloadManager.executeHlsTask()` 引用，删除前已 grep 确认无其他引用 |
| `android/app/src/main/java/com/qoder/cinema/download/NativeDownloadManager.java` | 删除 `executeHlsTask()` / `buildFilePath()`；`start()` 入口新增 HLS 硬封禁（:89-93）；`isHlsUrl()` 保留但仅用于入口拒绝（:254-257） |
| `android/app/src/main/java/com/qoder/cinema/DownloadPlugin.java` | `start()` 捕获 `UnsupportedOperationException`，返回 `E_UNSUPPORTED_FORMAT`（:107-111） |

**行为对比**

| 场景 | 改动前 | 改动后 |
| --- | --- | --- |
| `task.format === 'hls'` | JS `HlsDownloader` 处理（未变） | 同左，未变 |
| 非 HLS 任务但 URL 含 `.m3u8`/`.m3u` | 进入原生 `HlsDownloader`：忽略 `EXT-X-KEY`（`// TODO: AES-128 解密`），把加密分片按顺序拼接、rename 为最终文件并回调 `completed` → **产出坏文件且被标记完成** | `NativeDownloadManager.start()` 抛 `UnsupportedOperationException`，`DownloadPlugin` reject（`E_UNSUPPORTED_FORMAT`），**原生层不创建/不重命名任何输出文件**；JS 侧 `nativeDownloadStart` 失败后 `tryNativeDownload()` 返回 `false`，回落 JS 下载器 |
| 原生层 HLS 并发/取消 | HLS 任务不进活跃表，`pause`/`cancel` 对它无效 | HLS 任务在入口即被拒绝，不存在“原生 HLS 任务”这一状态 |

**取舍说明**

- 采用“删除 + 入口硬封禁”而非仅注释调用：`HlsDownloader` 是完整实现但缺少 AES-128 解密，保留代码存在被后续误接线的风险，故整文件删除（git 历史可追溯）。
- 原生拒绝后，JS 侧 `tryNativeDownload()` 会回落到通用 JS fetch。若上游把 HLS 任务误判为 `format !== 'hls'`，通用 fetch 可能把 manifest 文本落盘。该分支属于 `src/services/downloadEngine.ts`，本轮禁止修改；已在第 5 节列为需协调者分配给 DEV-01 的残留项。**原生层自身的坏文件路径已彻底关闭。**

**证据（改动后代码位置）**

- `NativeDownloadManager.java:28-33` 类注释说明 D-01 决策
- `NativeDownloadManager.java:82-93` `start()` 的 `@throws` 与 HLS 拒绝
- `NativeDownloadManager.java:254-257` `isHlsUrl()`
- `DownloadPlugin.java:104-112` 拒绝并返回 `E_UNSUPPORTED_FORMAT`

### 1.2 AND-16（P1）：所有下载任务统一登记、统一并发闸门与取消语义

**改动文件**：`android/app/src/main/java/com/qoder/cinema/download/NativeDownloadManager.java`

**机制变化**

| 维度 | 改动前 | 改动后 |
| --- | --- | --- |
| 活跃表 | 仅 `RangeDownloader` 任务写入 `activeDownloads`；HLS 任务完全不登记 | 所有被接受任务统一登记：`taskRegistry`（原始任务）、`pendingTasks`（排队）、`activeDownloads`（执行中）、`pausedTasks`（暂停） |
| 并发闸门 | HLS 任务绕过 `activeDownloads.size() < MAX_CONCURRENT` 判定 | 只有 `RangeDownloader` 任务存在；入口统一判定，`MAX_CONCURRENT=2` 对所有任务生效 |
| 排队暂停 | `pause()` 直接从 `pendingTasks` 删除，任务丢失 | 保留任务记录并加入 `pausedTasks`，`getStatus()` 返回 `paused`；`scheduleNextTask()` 跳过暂停任务 |
| 排队恢复 | `resume()` 对已删除的排队任务无任何动作 | 从 `pausedTasks` 取出并重新入队，有空位立即执行 |
| 执行中暂停后恢复 | `RangeDownloader.resume()` 只清标记，线程已退出，任务不再继续 | 暂停时保存原始任务；`start()`/`resume()` 会登记续传任务，旧线程 `finally` 后再调度，避免两个实例同时写 `.part` |
| 并发收尾 | `finally` 中 `activeDownloads.remove(taskId)`，可能误删恢复后的新实例 | 改为两参 `activeDownloads.remove(taskId, downloader)`，只清理自己（:243） |
| 服务生命周期 | 仅“active 与 pending 都为空”时停服务 | `stopServiceIfIdle()`：active 为空且无“可运行”的 pending（暂停任务不算）时停服务（:275-285） |
| 异常/完成 | 不清理任务登记 | `onCompleted()` / `onError()` 清理 `taskRegistry`、`pausedTasks`、`pendingTasks`（:293-296、:318-321） |

**行为对比**

| 场景 | 改动前 | 改动后 |
| --- | --- | --- |
| 同时启动 3 个任务 | 前 2 个执行，第 3 个排队（非 HLS）；HLS 任务不受闸门约束 | 统一前 2 个执行、第 3 个排队 |
| 暂停排队中的第 3 个 | 从 pending 删除，等同丢失；恢复无效 | 标记 `paused`，不参与调度；`resume` 后按队列顺序执行 |
| 暂停执行中的任务 | `RangeDownloader.pause()` 生效，`.part` 保留；但恢复通常无效 | `.part` 保留；恢复时以续传任务重新入队，由旧实例退出后统一调度 |
| 取消排队/执行中任务 | 排队任务删除；执行中 `cancel()` 删除 `.part`/`.sidecar` | 同左，并同步清理 `pausedTasks` / `taskRegistry` |
| 大屏/前端 `getStatus` | HLS 任务缺席，排队状态只有 `queued` | 所有任务可见；排队任务区分 `queued` / `paused` |

**证据（改动后代码位置）**

- `NativeDownloadManager.java:95-133` 启动与暂停恢复入口
- `NativeDownloadManager.java:138-151` 暂停（执行中/排队）
- `NativeDownloadManager.java:156-176` 恢复
- `NativeDownloadManager.java:181-192` 取消

## 4. 未做真机验证的显式声明

本轮**未在 Android 真机或模拟器上运行**，原因：任务仅要求在编译级收口，且 `RangeDownloader.java` / `LocalProxyPlugin.java` 处于 REV-01 评审冻结状态，避免设备侧行为变化干扰评审对象。

因此以下运行时行为**尚未验证**，需在 REV-01 完成后补设备验证：

1. 夸克真实接口返回结构是否与 `status/code/data/member_type` 解析完全一致（若接口字段名不同，校验会判失败，但不会误判成功——失败方向安全）。
2. 非夸克平台 cookie 抓取域名是否足够（当前 UA 平台取 `loginUrl` 的 origin）。
3. 暂停→恢复在真实网络下的 `.part` 续传一致性（依赖 frozen 的 `RangeDownloader`）。
4. 前台服务在 Android 15 dataSync 配额下的表现（D-04 按断点续传兜底，本轮未改动 `DownloadService`）。
