### 2.2 改法与取舍

**单一来源：仓库根 `package.json`。** `android/app/build.gradle:3-11` 新增：

```groovy
def pkgJson = new groovy.json.JsonSlurper().parseText(rootProject.file('../package.json').text)
def semverCore = (pkgJson.version ?: '0.0.0').toString().tokenize('-')[0]
def semverParts = semverCore.tokenize('.').collect { part -> part.isInteger() ? part.toInteger() : 0 }
while (semverParts.size() < 3) { semverParts << 0 }
def appVersionName = "${semverParts[0]}.${semverParts[1]}.${semverParts[2]}"
def appVersionCode = semverParts[0] * 10000 + semverParts[1] * 100 + semverParts[2]
```

`defaultConfig` 改为 `versionCode appVersionCode` / `versionName appVersionName`（`android/app/build.gradle:20-21`）。

- **为什么不是硬编码 `0.1.0`**：硬编码会再次产生两处来源；读取 package.json 后，Gradle 与 Vite `__APP_VERSION__` 同源，发版只改一个文件。
- **versionCode 语义**：`major*10000 + minor*100 + patch`，`0.1.0 → 100`。原安装包 versionCode 为 1，100 > 1，覆盖安装不降级；后续 `0.2.0 → 200`、`1.0.0 → 10000`，保持单调。
- **minSdk 不抬到 29**：本次明确维持 23（实际可运行下限），避免缩小安装面并把未验证设备排除在外。是否抬到 29 属于产品/发布决策，不在本轮。
- **NFR 文档不改**：按派单要求只提建议，见 §2.4。

### 2.4 NFR-C01 修改建议（由需求&方案统一更新，本次未改 `docs/01`）

建议把 `docs/01-需求/需求规格说明书.md:39` 与 `:778` 的表述改为：

> **NFR-C01**：Android 6.0（API 23）及以上可安装运行；**Android 10（API 29）及以上为已验证基线**。AC-53 继续在 Android 10 与 Android 14 设备上验收。

理由：代码事实是 `minSdkVersion=23`；当前没有 API 23–28 的真机验证记录。写成“API 29 及以上”会让用户与测试对安装范围产生错误预期；写成“23 可装、29 验证基线”既不缩小安装面，也如实披露验证范围。

如产品坚持“仅支持 API 29+”，则需要单独决策并同步修改 `variables.gradle`、回归矩阵与发布说明，**不应只改文档**。

### 3.3 DRM / 302 / 大文件专项结论

- **DRM（FIX-03 / Q-02）**
  - JS 侧由 DEV-01 并行修复；原生侧仍有两个缺口：**AND-14**（下载器不拒绝也不解密）与 **AND-21**（ExoPlayer 不做清单预检）。
  - 建议统一策略：**清单解析阶段**只要 `METHOD ∉ {NONE, AES-128}` 就失败；下载侧在写第一个字节前失败；播放侧在创建 hls/原生实例前失败。原生 HLS 下载器与 JS 下载器必须同一口径，否则“换条路径就能产出坏文件”。
- **302（FIX-04）**
  - JS 下载主清单走 LocalProxy 由 DEV-01 处理；本次修掉代理侧两个会放大 302 问题的缺陷（**AND-17**：最终 URL 作 base、EXT-X-KEY 重写）。
  - 原生 `RangeDownloader` / `ExoPlayerPlugin` 使用 OkHttp 且 `followRedirects` 默认开启（`ExoPlayerPlugin.java:70`），302 不是问题；原生 `HlsDownloader` 仍会用原 URL 解析相对分片（**AND-15**）。
- **大文件**
  - 多 Range 的“200 当成功”与“失败仍完成”是两个会造成**文件损坏**的缺陷，已修（AND-10/11）；取消残留 sidecar 会在下次续传造成空洞，已修（AND-12）。
  - 仍未收口：1 小时超时后的 rename（AND-13）、Android 15 前台服务配额（AND-03）、原生 HLS 分片 3 并发整段读入内存（AND-14 同一文件 `:99-121`，4K 分片内存峰值需真机观测）。
  - 这些结论**没有真机压力测试支撑**，仅来自代码路径与既有单测语义。
