### 2.1 为什么没有复制排期 / 存储 / 恢复（深度取舍）

现有链路（`notificationScheduler.ts` → Capacitor 插件）已具备下表能力，原生侧再造一份会形成**第二份状态源**，同一提醒可能重复通知：

| 能力 | 既有承担者 |
| --- | --- |
| 精确排期 + 非精确降级 | 插件 `LocalNotificationManager.setExactIfPossible`（`canScheduleExactAlarms()` false 时 `setAndAllowWhileIdle`，不抛异常） |
| 持久化 | 插件 `NotificationStorage`（SharedPreferences，键 `NOTIFICATION_STORE`，`id → 通知 JSON`） |
| 重启恢复 | 插件 `LocalNotificationRestoreReceiver`（`at` 已过期则改为 `now+15s` 后重排） |
| 点击回传 | 插件 `TimedNotificationPublisher` → `localNotificationActionPerformed` |
| 权限校验/申请 | 插件 `checkPermissions` / `requestPermissions`（`POST_NOTIFICATIONS`） |

→ 原生侧只补"渠道 + 能力快照"这两项不属于 JS 契约的状态，符合删除测试（删掉本类，渠道与诊断信息会在多处调用点重复出现）。

## 6. 契约疑问与需协调事项

> 按"不改契约、发现矛盾即上报"执行；以下均未单方面改动。

### C-01（P1，影响 AC-168 通知形态）前端未传 `channelId`，任务书 §3 的渠道实际不生效

- 现状：`src/native/notificationScheduler.ts` 的 `schedule()` 只传 `{ id, title, body, schedule, extra }`；插件因此用自建 `default` 渠道（`IMPORTANCE_DEFAULT`，名称 `Default`）。实测 TC-06 的 `importance =3` / `mName=Default`。
- 已验证：只要入参带 `channelId: 'programme_reminders'`，系统即按 `importance =4` 接收并响铃（TC-05）。
- 建议改动（**需协调者批准后由前端执行**，属 API-24 `schedule(item)` 入参扩展）：
  ```ts
  // src/native/notificationScheduler.ts → schedule()
  await mod.LocalNotifications.schedule({
    notifications: [{ id: item.nativeId, channelId: 'programme_reminders', /* 其余不变 */ }],
  });
  ```
- 在此之前，原生已把渠道建好（名称/重要性符合任务书），系统设置里会看到「节目提醒」渠道暂不承载通知。

### C-02（P1，任务书 vs 方案冲突）要求新建的 `NotificationSchedulerPlugin` 不会被调用

- 任务书要求新建 `NotificationSchedulerPlugin.java`（`scheduleReminder` / `cancelReminder` / `checkPermission` / `requestPermission`）+ `NotificationReceiver`；但：
  1. 方案 §3 API-24 明确「**不新增原生插件**」，原生侧仅允许 Manifest 增权限；
  2. 已交付前端 `notificationScheduler.ts` 调的是 `@capacitor/local-notifications@7`（插件名 `LocalNotifications`），不会调用自建桥；
  3. 自建桥必须自带排期/存储/receiver，会与插件形成**两份状态源**，同一提醒可能触发两次。
- 本批按方案执行，未建该插件、未建重复 BOOT receiver。若确需自建桥：请先修改前端 `notificationScheduler.ts` 与 API-24 契约（方法名/响应结构），再拆任务。

### C-03（P2，Android 14+ 准点风险）`SCHEDULE_EXACT_ALARM` 在 14+ 默认拒绝，且当前无引导入口

- 本工程 `targetSdk 35`：Android 14+ 对非闹钟/日历类应用**默认不授予** `SCHEDULE_EXACT_ALARM`，插件会静默退化为非精确闹钟（AC-168 的 ±60s 有风险）。
- 现状无引导：前端未调用插件的 `checkExactNotificationSetting`；且 `MainApplication.blockSettingsJump` 会吞掉 `android.settings.REQUEST_SCHEDULE_EXACT_ALARM`，即便将来加引导也需先开白名单（该守卫是安全设施，不能随意放宽）。
- 待裁决选项：a) 接受延迟，仅靠本记录 §6 与用户手册告知；b) 增 `USE_EXACT_ALARM`（自用分发、无商店策略约束，安装即授予；属权限面变更，需确认）；c) 前端加"精确闹钟"提示 + 原生放开该 settings 跳转（跨端改动）。

### C-04（P2）AC-170 需一次真机重启回归

见 TC-10：静态链路完整，运行期未验证（shell 不能发保护广播、设备无 root）。建议列入真机验收清单，与 AC-168 一并执行。

### C-05（环境）本机 EMUI「通知收纳」会吞掉提醒

见 TC-09。AC-168 的人工验收前必须先解除设备策略，否则会把环境问题误记为功能缺陷。

### C-06（措辞）任务书"跳转到提醒管理页"与 AC-168 不一致

任务书写"通知点击后打开 App 并跳转到**提醒管理页**"，AC-168 原文为"点击通知打开**直播页并定位该频道**（不自动播放）"，前端既有实现对后者。本批按 AC 执行，未改前端；如需改为提醒管理页，请先更新 AC。
