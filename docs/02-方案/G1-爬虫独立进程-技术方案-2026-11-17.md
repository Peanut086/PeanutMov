## 0. 结论与门禁

### 0.1 P0 spike 实测摘要

同一探针代码、同一批源，分别在生产进程 `com.qoder.cinema` 与 `com.qoder.cinema:spider` 执行：

| 源（api） | jar | native 承载 | 主进程 | `:spider` 子进程 |
|---|---|---|---|---|
| 苹果 • APP `csp_AppDrama` | xiaosa/spider.jar | 否 | 11 栏目 / 21 条 | **21 条**，`homeLen` 9211 / `catLen` 3815 与主进程逐字节一致 |
| 哔哩 • 视频 `csp_BiliYS` | xiaosa/spider.jar | 否 | 6 栏目 / 20 条 | **20 条**，长度同上完全一致 |
| 🚌巴士┃动漫 `csp_Dm84Guard` | jar/fan.txt（Guard 系） | 是 | 36 条 | 前提 1 未做时**子进程被打死**；做完后 **36 条** |
| 油管jar `csp_ProxySpider` | zq/pro.jar | 是 | `categoryContent` 30s 空转返回空 | 同样 30s 空转（**与进程无关**，是 9978/proxy 链路，见 §4） |

其余实测事实：

- 子进程 `MainApplication.onCreate` 会照常执行（实测 `appClass=com.qoder.cinema.MainApplication`），xCrash 因此在子进程里也生效。
- 子进程死亡后系统**不自动重启**；下次 `startService` 会重建（实测 pid 20525→21697→22969→5051），即"按需重生"是天然行为，不需要守护进程。
- 真内存错误（`Unsafe.putLong(0,0)` → SIGSEGV/SEGV_MAPERR）在子进程：主进程全程存活；`ApplicationExitInfo` 记为 `CRASH_NATIVE(5) status=11` + desc `null pointer dereference`；xCrash 写出 `..._com.qoder.cinema:spider.native.xcrash`；下次冷启动 `CrashNative` 正常摄取并解析出 `pname=com.qoder.cinema:spider`（文件名里的冒号不破坏解析），严格签名 `sig:0x0|libart.so` 与宽松签名 `lgs:11(sigsegv)|1(segv_maperr)|nolib|<thread>` 均落 prefs。
- 反面对照：`Os.kill(pid, 11)`（合成信号，`si_code=SI_USER`）只被记成 `EXIT_SELF(1) desc=null`，xCrash 有意跳过。**所以"子进程崩溃无法归因"不成立，但"探针必须用真内存错误才有归因意义"成立。**
- 跳转/悬浮窗：子进程 `startActivity` 不带 `FLAG_ACTIVITY_NEW_TASK` 直接抛 `AndroidRuntimeException`；带 flag 正常，`MainActivity` 是 `singleTask`，Activity 栈不增实例。`Spider.getActivity()` 在主/子都返回 null（本工程 stub），悬浮窗在主/子都是 `BadTokenException`（未申请 `SYSTEM_ALERT_WINDOW`，`canDrawOverlays=false`）→ **隔离不改变这两项现状**。
- 代价：子进程 PSS **83.4 MB**（主进程同态 169.7 MB）、RSS 188 MB；子进程冷启使首个 jar 加载 **+1.5~1.8 s**（主进程 749 ms → 子进程 2515 ms），后续调用与主进程持平。

### 0.2 两个硬前提（缺一个就是自杀式改造）

1. **子进程必须独占 WebView 数据目录**：Guard 系 jar 会往 main looper post 一个 `new WebView`（实测栈 `com.github.catvod.spider.merge.ME.run` → `WebView.<init>`），两个进程共用同一 data 目录直接 FATAL `Using WebView from more than one process at once with the same data directory is not supported`（crbug/558377）。解法 `WebView.setDataDirectorySuffix()`（API 28+，本工程 minSdk 29 已满足），**且必须每进程一次**。
2. **9978 与 Activity 归属**：`SpiderProxyServer.PORT = 9978`（`SpiderProxyServer.java:52`）只能被一个进程 bind，且 `SpiderProxyServer.start(this::routeProxy)` 在插件就绪时才拉起（`SpiderPlugin.java:775-777`）。子进程既不 bind 也没 Activity；依赖 9978 回环的爬虫（ProxySpider、以及 `initExt` 里写 `http://127.0.0.1:9978/file/xxx_cookie.txt` 读 cookie 的爬虫，实测见 `csp_BiliYS` 的 ext）在隔离态会直接退化。

### 0.3 实施触发门禁（三条全满足才立项动代码）

- G-1：OPPO Reno12 复验 + 3 天日常观察通过（判据沿用既有：0 个 `fault=0x7461642f` tombstone；`CheckReferenceResult` / `artQuickGenericJniEndTrampoline` 签名不再出现）。
- G-2：F2'/G2 的签名熔断 + jar 级隔离在真机日志里被证明**不足以**压住 native 崩溃（即"崩过熔断阈值的源仍反复打死主进程"）。若熔断已把闪退压到可接受，G1 的 83 MB 与 §4 的桥接工作量没有正当性。
- G-3：接受 §7 的分阶段口径（先只隔离"读"类调用），不接受全量隔离一步到位。

### 0.4 不纳入范围

- 不做 `Spider` 接口的重实现或代理层codegen；jar 侧保持"DexClassLoader + 反射"（`SpiderPlugin.java:1292` 起的既有加载链）。
- 不申请 `SYSTEM_ALERT_WINDOW`（悬浮窗在两个进程里都不可用是既有产品选择，不在本项夹带）。
- 不改 9978 对外协议（TVBox 约定，改了会打死壳子系爬虫）。
- 不为隔离引入新的前端状态存储；开关与熔断沿用现有 prefs / `getPrewarmState`（`SpiderPlugin.java:1053`）。

## 1. 架构总览

```
主进程 com.qoder.cinema                     子进程 com.qoder.cinema:spider
┌───────────────────────────────┐          ┌───────────────────────────────┐
│ WebView(Vue) → SpiderPlugin   │          │ SpiderWorkerService           │
│   ├ routeProxy / 9978 唯一持有 │  请求→   │   ├ WebView 后缀 = "spider"   │
│   ├ 任务派发（§3）             │ ───────► │   ├ 复用 loadSpider 同一实现  │
│   └ 结果回收 + 看门狗          │  ◄────── │   └ 只跑"读"类调用（§7 分期） │
└───────────────────────────────┘   结果←   └───────────────────────────────┘
        ▲                                            ▲
        └── xCrash / TombstoneParser / CrashNative ──┘（两进程都 init，实测已通）
```

要点：主进程保持"路由与协议"的中心（9978、Activity、播放器），子进程只做"把 jar 的解析算力搬出去"。F1 的同实例串行锁 `invokeLock`（`SpiderPlugin.java:416-420`）在子进程内继续生效，跨进程不需要新锁——每个 jar 实例只属于一个进程。

## 2. P1 进程与生命周期

**P1-1 承载体**：manifest 声明 `android:process=":spider"`、`android:exported="false"`、`START_NOT_STICKY` 的 Service。实测该配置不需要任何权限，`startService` 由主进程前台发起即可（应用可见态，绕开后台限制）。

**P1-2 WebView 后缀落点**（关键，放错就是回归）：写在 `MainApplication.onCreate` 的进程分支里，**不能**写在 Service 生命周期。

```java
// MainApplication.onCreate 最前（早于任何 jar 触碰 WebView；当前 xCrash init 在 :47）
String pname = Application.getProcessName();          // API 29+，minSdk 29 满足
if (pname != null && pname.endsWith(":spider")
        && Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
    WebView.setDataDirectorySuffix("spider");          // 每进程仅一次，重复调必抛 IllegalStateException
}
```

实测证据：把同一句放在 Service `onCreate`，进程复用时报 `Can't set data directory suffix: WebView already initialized`（E 轮 `webViewSuffix` 字段抓到）。

**P1-3 空闲退出**：子进程每次任务完成后由主进程下发"是否驻留"决策——驻留窗口 90 s（覆盖一次搜索的多源扇出），超时 `stopSelf`；同时接 `onTrimMemory`（内存压力 ≥ `TRIM_MEMORY_MODERATE` 立即退）。理由：83 MB 的常驻成本不可接受，但每条命令重建进程会把 +1.5~1.8 s 冷启摊到每次搜索。

**P1-4 首用延迟掩盖**：预热（`libraryService.warmupSources`，熔断档串行 + `PREWARM_SERIAL_STEP_DELAY_MS = 2000`，见 `src/services/prewarmState.ts:14`）本就跑在后台，让**第一次预热请求顺手把进程拉起来**，用户可感知路径（搜索/播放）不承担冷启。熔断态仍按 ≥2 s 错峰，不因隔离而放宽。

## 3. P2 任务通道与协议

**D-G1-01 通道选型 = AIDL 同步调用**（否决 Messenger 与文件轮询）：

| 方案 | 判定 |
|---|---|
| AIDL（`ISpiderWorker.ack(call)`） | ✅ 采用。请求有超时语义、结果有类型、进程死时 `RemoteException` 立刻可见（= 崩溃即时证据），与现有看门狗"超时只放弃 JS 回执、任务继续跑"的语义能对齐。 |
| Messenger | ✗ 单向异步 + 需自建关联 id 表，等于手写半个 AIDL。 |
| 文件 + 轮询（P0 探针所用） | ✗ 探针可用，产品不可用：轮询延迟、残留文件、无死进程感知。 |

**P2-2 载荷**：`jarUrl / api / initExt / ua / op / 参数数组`，全部是 `String`/`boolean`/`int`——TVBox `Spider` 的方法签名本就是 JSON 字符串进出（`homeContent(boolean)`、`categoryContent(String,String,boolean,HashMap)`、`detailContent(List<String>)`、`searchContent(String,boolean)`），**不需要 Parcelable 图**。实测最大 `homeLen` 9211 B、`catLen` 6206 B，Binder 1 MB 事务上限有 100 倍以上余量；仍设 512 KB 硬阈值，超限回落主进程（防止个别源返回超大清单打爆事务）。

**P2-3 超时/取消迁移**：现有插件层看门狗语义（F1 注释 `SpiderPlugin.java:416-420`）保持；跨进程后新增一层——主进程侧超时不取消子进程任务（僵尸任务继续，与今天一致），但**记录 `op` + jar 摘要进 `AppLog`**，让"子进程超时"与"子进程崩溃"在日志里可区分。

## 4. P3 9978、文件与 cookie 桥

实测事实：`csp_BiliYS` 的 `initExt` 含 `{"cookie":"http://127.0.0.1:9978/file/TVBox/bili_cookie.txt"...}`；Guard/壳子系爬虫同步请求 127.0.0.1:9978（`SpiderPlugin.java:178` 注释即为既有实证）。

- **P3-1 9978 留在主进程**（唯一 bind 方）。子进程爬虫的请求天然落到主进程 → `routeProxy`（`SpiderPlugin.java:823`）需要能路由给"**在子进程里加载的**"爬虫：新增跨进程反查——主进程维护 `jarKey → ownerProcess` 表，命中子进程时经 AIDL 反向调用 `proxy(params)`，同步等待（沿用现有 owner 优先级与 `do` 归属逻辑 `SpiderPlugin.java:864`）。
- **P3-2 `/file/` 与 cookie 读写**：由主进程代理（子进程只发 HTTP，不碰存储），因此现有 `SpiderProxyServer.java:314` 那条"404 会让爬虫以为端口死了、扫遍 9978-9999 后降级"的行为必须原样保留——**桥未就绪前不得把任何依赖 9978 的爬虫搬进子进程**（P0 实测的 ProxySpider 30 s 空转就是这个缺口的直接体现）。
- **P3-3 磁盘共享**：jar 缓存与 dex 优化目录两进程同路径（`/data/data/.../files/...`），实测在子进程内直接可读、加载成功；但 `SharedPreferences` **不跨进程**（既有 `crash-native-prefs` / `spider_debug_log` 等一律只由主进程读写，子进程要状态须由主进程随请求下发）。

## 5. P4 取证与熔断复用（几乎零改动，一处必须改）

- ✅ 已实测可复用：xCrash 无条件 init（`MainApplication.java:41-47`）→ 子进程 native tombstone + Java tombstone 都有；`CrashNative` 摄取与双签名（G2）照常在主进程完成；`LogsView` 导出包（G4/G6）自动带上，用户侧不需要 adb。
- 🔧 **必须改：签名 key 加进程命名空间**。今天严格签名是 `faultAddr|firstSoFrame`、宽松签名是 `signal|code|culpritSo|thread`，两者都**不含进程名** → 一旦子进程崩溃与主进程某次崩溃撞同一 `fault|so`，熔断计数会互相污染（要么误熔断预热，要么漏判）。落点：`CrashNative` 的 prefs key 前缀加 `pname` 归一段（`main` / `spider`），历史 key 不迁移、自然过期。
- ✅ 保持不变：`checkLastExit` 按进程名等值过滤（`MainApplication.java:240`）——子进程崩溃**不应**把主进程推进安全模式（实测确认这条过滤已经给了正确行为）。
- 📤 导出侧仅需把子进程 tombstone 的 `pname` 显示出来（现有命名已带 `com.qoder.cinema:spider`，不用改解析）。

## 6. P5 开关、入口与降级

- **默认关**。开关系 `spider_isolated_worker`（prefs），关闭态代码路径 = 今天的单进程路径，不新增分支风险。
- **入口可达性**（遵循既有红线"修复 X 的入口不能被 X 挡住"）：开关放**设置页 → 爬虫/源设置**分组，不放播放页；闪退发生在爬虫加载时，用户仍能从设置进入，不需要 App 先"稳定启动"。
- **自动降级**（不是用户可见的"安全模式"UI——该项此前已被否决）：子进程连续 2 次异常退出（AIDL `RemoteException` 或任务超时）→ 本轮会话内该 jar 回主进程执行，并在日志记一行归因；不弹任何提示。
- 与熔断交互：`throttledUntil` 期间隔离**照常**，错峰节奏（2 s）不因换进程而放宽——P0 未测"熔断态 + 子进程"的复合态，实施时要补测。

## 7. 分期与验收

**G1-a（先做，风险最小）**：只把 **`homeContent` / `categoryContent` / `searchContent` / `detailContent`** 派给子进程——native 崩溃的头号嫌疑（jar 加载 + 解析 + Guard 的 native 状态）都在这一层；`playerContent` 与 `proxy()` 留主进程。
验收：
1. 真机 4 源（xiaosa×2 / fan-guard / pro）隔离前后**内容逐字节一致**（对照 `homeLen`/`catLen`，P0 已给出基线：9211/3815、2176/3292、9599/6206）；
2. 20 次冷启动压测 0 新 tombstone；搜索 + 首页 + 详情三段逐项通过；
3. 门禁：子进程 PSS 增量 ≤ 90 MB；隔离态首个搜索请求 P95 延迟劣化 ≤ 200 ms（进程已驻留时）；
4. 熔断/错峰在隔离态复验（≥2 s 间隔、`JS:` 日志行仍在，即 G6/G7 不回归）。

**G1-b（G1-a 通过且 G-2 成立才做）**：§4 的 proxy 反查桥 + `playerContent` 进子进程。

**回滚**：关开关即回到 G1-a 前的路径；代码保留一个版本不做删除式回滚。

## 8. 工作量与风险

| 项 | 量级 | 主要风险 | 缓解 |
|---|---|---|---|
| P1 生命周期 + WebView 后缀 | 0.5 d | 后缀放错位置 → 进程复用抛 `already initialized` | 落点钉死在 `MainApplication.onCreate`，加单测/冷启断言 |
| P2 AIDL 通道 + 超时 | 1.5 d | 僵尸任务语义漂移（看门狗行为变化） | 不新增取消逻辑，只加日志区分 |
| P3 9978 反查桥 | 2~3 d | 破坏壳子系爬虫（404 → 端口扫描降级） | 分期：G1-a 不搬 proxy |
| P4 签名命名空间 | 0.5 d | 与历史 prefs key 并存 | 不迁移、自然过期 |
| P5 开关 + 自动降级 | 0.5 d | 入口可达性 | 放设置页，不进播放页 |
| 真机验收（华为 + Reno12 + MuMu） | 1 d | 设备态差异（`MANAGE_EXTERNAL_STORAGE` 会被 `install -r` 重置） | 验收脚本现查 `appops get` |

合计约 6~7 人日（G1-a + G1-b），其中 **30% 的风险集中在 §4**——这也是建议先等熔断/隔离实测数据、而不是一次搬全量的原因。
