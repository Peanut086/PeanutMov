## 4. 归属判定（PM 指定的两处"不要硬改"）

### 4.1 `hlsDownloader.spec.ts` 的 `persistIntervalMs`（8 处）

**判定：测试写超前，不是实现丢能力。**

依据：

1. `HlsDownloaderDeps`（`src/services/hlsDownloader.ts:19-29`）**从该夹具引入那次提交（`e4545b8`）至今 HEAD 从未声明** `persistIntervalMs`；`git show e4545b8|98d19f7|2d35a7a:src/services/hlsDownloader.ts` 三处均无该字段。
2. 该字段只存在于 `DownloadEngineDeps`（`src/services/downloadEngine.ts:39`，节流值 `DOWNLOAD_PROGRESS_PERSIST_MS = 2000`）；HLS 下载器内部固定 `>= 1000`（`hlsDownloader.ts:554`，用例标题「每 1 秒上报一次进度」与之吻合）。
3. 8 处传参在运行期被 JS 忽略，用例一直是绿的——即"传了但不生效"，属入参照抄 `DownloadEngine` 的笔误；若真丢了能力，用例本身应失败而不是仅 TS 报错。
4. 结论：移除这 8 个入参，断言语义不变（用例仍通过）。**遗留观察（交评审阶段，不在本任务下结论）**：下载器把节流写死 1000ms 而引擎侧走常量 2000ms，两处口径不一致，建议评审时确认是否需要注入。

### 4.2 `tests/player/*` 断言冲突（`nativeEngine.spec.ts` 600ms）

**判定：实现有意变更，测试未跟进（测试旧了）。**

依据：

1. `PROGRESS_POLL_MS` 在 `bead00b`（用例与实现同时引入）为 **500**，`98d19f7`「P0-P4 播放下载全链路性能优化」改为 **1000**，此后未变。
2. 用例在 `await vi.advanceTimersByTimeAsync(600)` 后断言 `onTimeUpdate` 被调用——600 < 1000，定时器不可能触发，失败表现为 "Number of calls: 0"，与实现的行为语义（新增 `ready` 门控后仍按 1s 轮询）无矛盾。
3. `PlayerControllerGuard` 的断言冲突（#16）相反：那是**真实缺陷**（预检链路被注释掉），不是测试旧了——由 `git diff` 可见基线 `PlayerController.ts` 写有「P0-4: 不再预拉清单」，DEV-01 已恢复。
4. 结论：只改用例的推进时长（600 → 1100），断言原样保留。
