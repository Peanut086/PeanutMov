## 1. 预算可配置（改前 → 改后）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 单源超时来源 | 适配器自报 `searchTimeoutMs`（站点 8s / 爬虫 20s / 其它 5s）硬编码 | `resolveSearchTimeoutMs(自报值, 设置档位)`，档位来自 `settings.searchBudget` |
| 默认行为 | 8s / 20s / 5s | **不变**（`standard` 倍率 1，逐字等价，含未设置过该字段的旧数据） |
| 可调档位 | 无 | 快速 0.6 / 标准 1 / 耐心 1.5，钳制区间 [3s, 30s] |
| 生效值（站点 / 爬虫） | 8s / 20s | 快速 5s / 12s；标准 8s / 20s；耐心 12s / 30s |
| 设置入口 | 无 | 设置 → 内容 → 搜索超时预算（BottomSheet 每档展示实际秒数） |

设计要点：

- 只缩放「等多久」，不改超时语义：到点仍 `AbortController.abort()`，该源计入失败列表，可被「重试失败源」单独捞回；
- 下限 3s 防止快速档把站点源模板请求本身误杀；上限 30s 防止耐心档让长尾源重新拖住整轮聚合；
- 非法输入（`undefined`、非正数、未知档位）一律回落，函数任何输入都返回可用毫秒数，不抛错；
- `libraryService` 读取设置失败（DB 异常）时 `searchBudgetPreset()` 返回 `undefined` → 等价 `standard`，搜索不受影响。

## 2. 失败源汇总与默认折叠（改前 → 改后）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 位置 | 结果列表**底部**一条黄条 | 结果**顶部**置顶面板（空结果态同样展示） |
| 明细 | 点「明细」弹 BottomSheet，逐源一行、无折叠概念 | 面板内逐源列表**默认折叠**，箭头展开/收起（`aria-expanded` + `aria-controls`，DOM 常驻保证关联可解析） |
| 一句话原因 | `guidanceOf().title` 聚类，最多 2 类 | `summarizeSearchFailures`：按 sourceId 去重后聚类，最多 2 类（`SEARCH_FAILURE_REASON_LIMIT`），同一分类口径（`classifySourceFailure`） |
| 重试 | `retryFailedSources` 语义已存在但按钮文案「重试」，无「只重试失败源」的显式表达；无并发/守卫 | 按钮文案「重试失败源」；`sourceIds` 只含失败源、`forceAll` 跳过体检过滤；重试中/主搜索进行中禁用；整体失败 toast |
| 组件复用 | 逻辑内联在 `SearchView`，两处重复标记 + 一套死样式 | 收敛为 `SearchFailurePanel`，`SearchView` 只接 `failures`/`nameOf`/`retrying`/`busy` + `@retry` |

`SearchFailurePanel` 文案示例：标题「33 个源搜索失败」，副行「33 源站已失效 · 5 规则脚本异常」，展开后每行「源名 + 分类标签 + 收敛后的 detail（脚本内部异常替换为统一文案，不外泄堆栈）」。

## 7. 未测项与需协调者确认（不自行变通）

1. **真机长跑未复现**：手头环境没有稳定的「30+ 失败源」样本（演示源正常返回），折叠/重试的**交互视觉**与真实耗时（能否从 ~20s 降到可感知下降）需 QA 在真机热门词场景回归；本记录中相关用例为 mock 桩。建议验收动作：热门词搜索 → 顶部出现失败面板 → 展开核对源名/分类 → 点「重试失败源」→ 观察仅失败源被请求（DevTools/logcat 可见 `sourceIds` 只含失败源）。
2. **`AppSettings.searchBudget` 属于契约外新增字段**：API-10 设置契约未定义该字段。为满足 OPT-04「预算可配置」且不破坏向后兼容，按**可选字段**加入（缺省 = standard，行为与旧版一致），旧备份/旧数据库无需迁移。若评审要求走契约变更流程，请协调者确认后再合并到 API-10 文档术语；如需改为独立 kv 键，本模块只依赖 `settingsService.get()`，替换成本为 1 处读取。
3. **「失败源所在的结果分组默认折叠」未实现（口径请确认）**：任务表述提到「失败源（health !== 'ok' 或 timeout）的分组默认折叠」。现状多数源 `health === 'unknown'`（未体检），若按 `health !== 'ok'` 折叠分组，会把大量**有正常结果**的源折叠掉，直接伤害检索可用性；且失败源本身往往没有结果可折叠。因此本次实现为「失败源清单折叠」+「汇总置顶」，未按源健康度折叠结果分组。若验收口径确实要求按 health 折叠结果组，请明确 `unknown` 的处理（建议仅折叠 `unreachable`/`bad_config`/`auth_failed`），我再补实现与用例。
4. **重试整体失败时的提示文案**：「重试失败源未成功，可稍后再试或到源管理检查」走 `appEvents` toast（type=info）。若产品要求区分「源站已失效」与「临时超时」两类提示，需要新的 UI 文案表，属设计规范变更，未自行新增。
