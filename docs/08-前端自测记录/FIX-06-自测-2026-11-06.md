## 1. 实现口径

### 1.1 触发链路

```
App 启动
  main.ts → initSubscriptionAutoRefresh()
             ├─ subscriptionLifecycleService.autoRefreshIfDue('startup')   ← 立即触发一次
             └─ subscriptionLifecycleService.bindAutoRefresh()             ← 只接线一次（幂等）

App 回前台（Capacitor appStateChange / Web visibilitychange ← @/native/appLifecycle）
  → onAppStateChange 回调（仅 active 且状态确有变化时）
      → subscriptionLifecycleService.autoRefreshIfDue('resume')
          → 闸门判定 → maybeAutoRefresh()（既有实现：并发 ≤2、失败静默）
```

- 只做「切到前台」触发，进后台不做事；同一状态重复上报（重复 visible）被 `lastAppState` 过滤。
- 复用 `@/native/appLifecycle` 的 `onAppStateChange`（全仓唯一生命周期入口），未新增 DOM/插件监听。

### 1.2 TTL 去重与并发去重（触发层）

| 场景 | 判定 | 结果 |
| --- | --- | --- |
| 距上次**发起**刷新 < 24h（`SUBSCRIPTION_REFRESH_TTL_MS`） | `autoRefreshRunAt` | 跳过，`skipped: 'ttl'`，不读库不联网 |
| 已有在途刷新 | `autoRefreshInFlight` | 复用同一 Promise，`skipped: 'inflight'`，不重复拉取 |
| 离线 | `isOnline()` | 跳过，`skipped: 'offline'`，且**不占用** TTL 闸门（联网后回前台可补触发） |
| 到期且在线 | — | 真正执行 `maybeAutoRefresh()`，`triggered: true` |

- 启动与回前台共用同一个闸门，因此启动后 24h 内回前台不会二次拉取；超过 24h 回前台补触发。
- 闸门只存内存（`autoRefreshRunAt`）：进程重启即由启动触发兜底；逐订阅的 TTL 时间戳仍存在 kv
  `subscription-refresh-state`，重启后 `maybeAutoRefresh()` 的 due 为空直接返回，不会真的重复拉取。
- 刷新失败（含抛错）不回退闸门，避免「每次回前台都重试」变成请求风暴；未刷成功的订阅没有新时间戳，
  下个 24h 窗口仍会被扫到。
- 手动刷新（源管理页「刷新全部」→ `sourceStore.refreshAllSubscriptions`）仍直接走 `maybeAutoRefresh()`，
  不受触发闸门限制（用户主动操作不应被 24h 挡住）。

### 1.3 长时间运行稳定性

- 无常驻定时器，无轮询；监听器由 `appLifecycle` 单例持有，`bindAutoRefresh()` 幂等（重复调用返回同一 unbind）。
- `autoRefreshIfDue()` 内部吞掉所有异常（`maybeAutoRefresh().catch(...)`），调用点 `void` fire-and-forget，
  不会产生 unhandled rejection。
- `__resetAutoRefreshState()` 会解绑监听并清空闸门（测试/热重载用），避免跨用例/跨上下文串味。

测试实现说明（非业务口径变动）：

- 用例用 `vi.spyOn(subscriptionLifecycleService, 'maybeAutoRefresh')` 截断真实刷新链路，不碰 IndexedDB / 网络，
  只验证「触发层」；逐订阅 TTL 语义由既有 `subscriptionLifecycle.spec.ts` / `importService.spec.ts` 覆盖。
- 24h 边界用 `Date.now` 叠加可控偏移模拟，不使用 fake timers（避免影响 IndexedDB 异步链路）。
- 回前台事件走真实 `document.visibilitychange`（`appLifecycle` 的 Web 兜底），与 `downloadLifecycle.spec.ts` 同一手法。
- `dispatchEvent` 是同步的：回前台回调会在第一个 await 前落闸门，因此断言前先 `flush()` 让在途刷新落地，
  否则下一次回前台会被**正确地**合并到在途任务而看不到新调用（已在用例注释中说明）。

## 4. 未覆盖 / 待真机确认

1. **Android 原生 `appStateChange`**：单测环境为 happy-dom，走的是 `visibilitychange` 兜底分支；
   原生分支（`@capacitor/app`）需要在真机上做一次「切后台 30s → 回前台」观察日志
   `订阅自动刷新…`（TTL 已过期时）确认触发，建议并入本批真机回归。
2. **跨 24h 的真实等待**未实测（用例用时钟偏移模拟），真机验证建议临时调小 TTL 或直接看 kv
   `subscription-refresh-state` 时间戳变化。
3. 触发闸门不落库：App 进程重启后闸门清零，由启动触发补一次。此行为符合 Q-05=A「启动 + 回前台」口径，
   但若后续要求「重启也遵守 24h」，需另立需求把 `autoRefreshRunAt` 落到 kv（本次未做，避免扩大改动面）。
