## FIX-B：healthService 子集检测快照合并（REV-41）

### 问题

`executeCheck(ids)` 在子集检测（`ids !== undefined`）时，直接用仅含子集结果的 `snapshot` 替换 `cachedSnapshot`。导致：

1. 未被检测的源丢失 `latencyMs` 数据
2. `latencyOf(otherSourceId)` → null
3. `healthTierOf('ok', null)` → 退化为 `bad`
4. UI 上健康源误显红色"正常"角标

### 修复

`healthService.ts:47-57`：当 `ids !== undefined && cachedSnapshot` 存在时，将新结果**合并**到已有快照：

```typescript
if (ids !== undefined && cachedSnapshot) {
  const merged = { ...cachedSnapshot.results, ...results };
  cachedSnapshot = {
    checkedAt: Date.now(),
    results: merged,
    failedCount: Object.values(merged).filter((r) => r.health !== 'ok').length,
  };
  return cachedSnapshot;
}
```

`checkAll`（`ids === undefined`）行为不变，仍整体替换。

| --- | --- | --- |
| check(ids) 后未检测源数据保持 | latencyOf(a)=120, tierOf(a) 不变 | ✅ |
| 无缓存时 check(ids) 正常创建 | 快照含 1 条结果 | ✅ |
| checkAll 仍正常替换 | 二次 checkAll 后 latency 全部更新 | ✅ |

## FIX-C：NativeDownloadManager 排队暂停任务恢复（REV-42）

### 问题

`start()` 在 line 115 检查 `pendingTasks.containsKey(taskId)` 时直接 return，未区分"正常排队"与"排队中被暂停"。场景：

1. 任务 X 创建 → `pendingTasks={X}`
2. `pause(X)` → `pausedTasks={X}`（X 仍在 pendingTasks）
3. `start(X, ...)` → 命中 `pendingTasks.containsKey` → **直接 return**
4. X 永远卡在 `pausedTasks`，无法恢复

### 修复

`NativeDownloadManager.java:117`：增加 `!pausedTasks.containsKey(taskId)` 条件，暂停中的排队任务不走 early return，改由下方正常路径（line 122-135）清除 `pausedTasks` 并重新调度。

```java
if (pendingTasks.containsKeyId(taskId) && !pausedTasks.containsKey(taskId)) {
    // 仅"正常排队且未暂停"时跳过
    return;
}
```
