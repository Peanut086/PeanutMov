## 1. 实现口径

### 1.1 清单拉取链路

```
HlsDownloader.run()
  ├─ fetchManifestText(task.url, …)          ← 主清单
  │    ├─ 原生（isNative()）且非回环地址：GET `${proxyBase}/${encodeURIComponent(url)}`
  │    │    ├─ 2xx → { text, baseUrl: 落地地址或请求地址 }
  │    │    └─ 非 2xx / 抛错 → warn + 回退直连（取消信号仍生效）
  │    └─ 直连 GET url（带任务请求头）→ 非 2xx 抛 mapHttpError；2xx → { text, baseUrl }
  ├─ assertSupportedKeyMethods(text)          ← FIX-03/AC-40 守卫，解析前拦截
  └─ parseM3u8(text, document.baseUrl) → unwrapPlaylistUrls(playlist, proxyBase)
```

- 清单与分片/密钥/初始化分片使用**同一个**代理入口与地址形态（`${proxyBase}/${encodeURIComponent(url)}`），
  未引入第二种调用方式；代理 token 生命周期、LRU、回退策略均不变。
- 代理优先的拉取方式在 DEV-01 已落地于 `fetchManifestText()`；本次复核确认主清单、子清单都只经该入口，
  不存在 `fetchImpl(task.url)` 裸直连分支（裸 URL 只作为代理不可用时的回退）。

### 1.2 解析基线归一化（本次核心修复）

清单里的相对引用（`720p.m3u8`、`seg0.ts`）必须相对**302 落地地址**解析。修复前两处解析一律使用
`task.url` / `selected.url`：`/master.m3u8 → 302 → /real/dir/index.m3u8` 时会把 `seg0.ts` 拼成
`/seg0.ts`（404）。现按 `manifestBaseUrl()` 归一：

| 场景 | `response.url` | 采用基线 | 说明 |
| --- | --- | --- | --- |
| 直连、跟随 302 | 落地地址 `https://cdn/real/dir/index.m3u8` | 落地地址 | `fetch` 默认跟随跳转，`response.url` 即落地地址 |
| 直连、无跳转 | 请求地址 | 请求地址 | 与落地地址等价 |
| 代理路径（原生已改写清单） | 回环 `http://127.0.0.1:PORT/p/{token}` | 请求地址 | 回环地址只有 token、不含上游路径语义，**绝不能**当基线；相对引用此时已被原生侧按落地地址改写成 `/p/{token}/{编码后的绝对地址}`，JS 由 `unwrapPlaylistUrls()` 还原绝对地址，基线不参与拼接 |
| 代理原样透传（未改写，清单仍含相对引用） | 回环 | 请求地址 | 兜底：相对引用按请求地址解析，**不会**拼出 `127.0.0.1/p/token/seg0.ts`；此分支 JS 侧无法得知落地地址，已知边界见 §4-2 / §5-Q1 |
| `response.url` 缺失或非 http(s) | `''` / 其他 | 请求地址 | 防御性回退 |

- 规则收敛在一个纯函数 `manifestBaseUrl()` 内，主清单与子清单共用，避免两处口径漂移。
- 子清单同理：变体清单自身也可能被签名地址 302，基线取其拉取时的落地地址。

### 1.3 取消与 DRM 守卫顺序（保持不变）

- `fetchManifestText()` 入口与两条路径的 `catch` 均判定 `signal.aborted` → `E_ABORTED`，暂停/取消不会挂在清单请求上。
- `assertSupportedKeyMethods()` 仍在 `parseM3u8()` 之前、任何分片/密钥请求之前执行；
  302 链路因此同样「一个字节都不写」即抛 `E_DRM_PROTECTED`（用例 5 断言 `blobRepo.get()` 为 `null`）。
- 未改动 `mapHttpError()`：302 不再以 `E_NETWORK` 形式落到业务层，其余 4xx/5xx 映射与错误文案不变。

## 4. 未覆盖 / 待真机确认

1. **真机 `CapacitorHttp` + 302 未复测**：单测用 mock `fetchImpl`，不经过原生拦截层。需在 Android 真机用
   一个 `GET /master.m3u8 → 302` 的真实地址跑一次下载，确认请求确实落到 `127.0.0.1:PORT/p/{token}`、
   且分片按落地目录拉取（观察 `logger` 中不再出现 `E_NETWORK`）。
2. **代理原样透传含相对引用**：此分支 JS 侧无法得知 302 落地地址（原生插件只回传回环地址，`response.url` 无上游语义），
   只能回退为「按请求地址解析」。真实 `LocalProxyPlugin` 会以落地地址为基线改写清单，正常链路不会走该分支；
   但插件旧版本/改写失败时会退化为按请求地址解析，需插件侧补充信息才能彻底闭合（见 §5-Q1）。
3. **REV-40 P2（4xx 回退广度）未改**：目前代理返回任意非 2xx 仍回退直连。本次只要求 302 链路可用，
   为避免顺带改变错误语义，未收紧为「4xx 不回退」；如需收紧请协调者给口径。
4. 清单体积上限、代理 token LRU 淘汰等属原生侧行为，本次未涉及，未做真机压测。

## 5. 对契约 / 设计的疑问（上报协调者）

- **Q1（建议原生侧补充字段，本次不实施）**：`LocalProxyPlugin` 未把 302 跟随后的最终地址暴露给 JS，
  导致前端无法在「清单被原样透传」分支上做精确归一化。建议原生侧在清单响应的路径形态下回传落地地址
  （例如响应头 `X-Local-Proxy-Final-Url`，或 `/p/{token}` 返回 `{ body, finalUrl }`）。该改动位于
  `android/app/src/main/java/com/qoder/cinema/LocalProxyPlugin.java`，超出本任务允许修改的文件范围，故未实施，
  前端侧已按 §1.2 的表格做当前可达的归一化（含「回环地址绝不作基线」的护栏）。
- **Q2（口径待确认）**：`fetchManifestText()` 在代理返回 4xx 时也回退直连（REV-40 已记为 P2）。若 CDN 对清单
  稳定返回 403（防盗链），回退直连会把 403 变成 `E_NETWORK`（CapacitorHttp 层的表现），错误码口径是否需要区分？
  本次保持现状未改，等待口径。
