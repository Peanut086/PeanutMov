## 1. 关键决策与偏差（逐条理由 + 影响）

1. **`src/services/settingsService.ts` 超出原允许文件清单（已实施，需协调者确认）**
   原因：`sanitize()` 会重建整个 `AppSettings`，未在白名单里的字段会被丢弃；不补 `sanitizeBackup()` 的话，`backup` 配置一写就丢（`update` 与 `load` 双向丢），定时/加密功能无法持久化。
   改动面：仅追加一个字段的清洗逻辑（模式白名单、小时 0-23、星期 1-7、保留数收敛 1-20、无 salt/verifier 则强制 `encryptionEnabled=false`、时间戳非法置 null），不触碰任何既有字段。
   若不接受：需由协调者改回并另派 settingsService 的修改任务，本任务功能会失效。

2. **备份索引落在既有 `kv` 存储，而非新增 IndexedDB `backupRepo`**
   原因：任务禁止改 DB schema/迁移，`src/db/schema.ts` 不在允许清单。索引 key `backup-index`，Web 端备份正文 key `backup-file:<id>`（原生端写 App 数据目录 `backups/`）。
   影响：同一份数据语义（"本机备份"），但排查时要在 `kv` 表里找；后续若要独立 object store，可写一次迁移把 kv 的 `backup-index` 搬过去。

3. **"密码不能明文存储"的具体口径**
   落盘内容只有三样：① `encryptionSalt`（base64）；② `encryptionVerifier`（对固定串 `peanutmov-backup-key-check` 加密得到的 `iv.cipher`，用来校验输入密码是否正确，不含密码信息）；③ `backup-encryption-key`（base64 的 **PBKDF2 派生密钥**，供无人值守的定时备份使用，不是密码）。
   密码本身零存储：不写 settings、不写 kv、不进日志；恢复 `.enc` 备份一律由用户重新输入密码 + 文件头 salt/iterations 重新派生，因此**换机也能恢复**。
   残留风险（需知悉）：派生密钥以可导出 base64 形式存在本机 kv 中，能读 IndexedDB 的攻击者可解本机历史备份——这是"无人值守加密备份"的必要代价；若要求更严，可改为"关闭加密即失效 + 每次定时备份要求解锁"，需产品决策。

4. **App 未运行时的能力边界**
   JS 在 WebView 被回收后不会执行，原计划提到的 AlarmManager 属 Android 原生改动（本任务禁改）。因此实际链路是：原生侧用 `LocalNotifications` 在"下次触发时间"安排一条提醒（`allowWhileIdle`，需通知权限，被拒则静默降级）→ 用户打开 App 后由 `startBackupScheduler()` 的补执行（`lastScheduledAt < 最近一个计划点`）立即补做。
   影响：不会"到点自动备份"，只会"到点提醒 + 打开即补"。要做到真后台执行，需原生 Worker/WorkManager 派单。

5. **版本保留只清理受管理命名**：`backup_YYYYMMDD_HHmmss.json|.enc`；本机与云端**分别**保留最近 N 份；既有手动导出文件 `peanutmov-backup-*.json` 永不被自动删除（避免误删用户主动导出的存档）。

6. **调度器启动钩子放在 `settingsStore.load()`**：`main.ts` / `stores/bootstrap.ts` 不在允许清单，而 `App.vue` 在 `onMounted` 调 `settings.load()`。用动态 import + `try/catch`，调度器不可用不影响设置加载；构建后 `backupScheduler` 被拆成独立 chunk（见 §7.3），不增加主包体积。

7. **页面卸载不调用 `stopBackupScheduler()`**：调度器是 App 级单例，页面卸载就停会漏掉后台定时备份；页面只清理自己的 `setInterval`（"下次备份"相对时间）与 `settings:changed` 订阅。

8. **加密后的文件仍以 `application/json` 上传 WebDAV**：`.enc` 的内容是 JSON 外壳，MIME 用 `application/json` 便于 `WebDAVClient` 与既有云端列表复用；扩展名仍然是 `.enc`。

9. **UI 细节偏差（为了让新代码"零非 token 值"）**：行高统一写 `calc(var(--touch-min) + var(--space-3))`（= 56px，与既有 `.backup-toggle` 视觉同高，但不再出现裸 px）；两行文案微间距由既有代码的 `2px` 统一为 `--space-1`（4px）；列表锁图标尺寸用 `1em`（随 `--text-label-strong`）。`BackupView.vue` 里既有的 `56px / 120px / 28px / 40px / 2px` 属原文件遗留样式，本任务按要求未改动。

数据流（定时）：`settingsStore.load()` → `startBackupScheduler()` → 60s tick / 回前台 / 设置变化 → `isBackupDue(settings.backup, lastScheduledAt)` → `backupService.runBackup({source:'scheduled', local:true, webdav:已配置})` → 写索引 + prune → `lastScheduledAt/lastBackupAt` 落 settings → `settings:changed` → 页面刷新列表与密钥状态。

数据流（加密）：用户输入密码 → `setupBackupEncryption(password)` → PBKDF2(150000) 派生 → 派生密钥写 kv、salt+verifier 写 settings → `encryptionEnabled=true`；此后 `runBackup` 用缓存密钥加密（复用已存 salt）。

## 4. 三态与异常数据

| 层级 | 加载中 | 空数据 | 失败 | 异常数据 |
| --- | --- | --- | --- | --- |
| 备份列表 | `LoadingSpinner` + 「加载备份列表…」 | 「暂无备份版本，点击上方…生成第一份」 | `.backup-error` + 「重试」（不清空已有列表内容之外的上下文） | 索引条目经 `normalizeRecord` 清洗：非对象 / 缺 `id`/`path` / 时间非数字直接丢弃；未知 `source`→`manual`、未知 `location`→`local` |
| 定时设置 | 保存中 `busy` 禁用全部控件 | 关闭态即"空"：不展开字段，只显示一行说明 | 保存失败 → toast；**定时执行失败**只写 `settings.backup.lastError` 并在组件内红条展示，不弹窗、不阻断 | 小时越界收敛 0-23、星期 1-7、保留数 1-20（`normalizeSchedule` 与 `sanitizeBackup` 双重收敛） |
| 加密设置 | 派生密钥中按钮显示「处理中…」并禁用 | 未启用时只显示开关 + 说明 | 启用/改密失败 → toast（如密码 < 8 位在组件内先拦截，不发请求） | `encryptionEnabled=true` 但 kv 里没有派生密钥 → 显示「本机密钥未就绪」，此时立即备份会明确报「加密密钥不可用，请重新设置备份密码」 |
| 备份执行 | 按钮内 spinner + 「备份中…／上传中…」，其余入口禁用 | — | 手动失败 → toast 带真实原因；定时失败 → 落 `lastError` | `encrypted` 且无密钥、WebDAV 未配置、备份内容为空都抛 `AppError` 并在 UI 可见，不静默成功 |
| 恢复 | 面板按钮「正在恢复…」，其它恢复/删除禁用 | — | **密码错误**：面板内红条「密码错误或备份文件已损坏」+ toast，输入框与上下文保留；版本不支持 → 「加密备份版本不支持，请升级 App」 | 非外壳 JSON / 空文件 / 记录已被删除分别给「备份文件格式不支持」「备份文件为空」「备份记录不存在，请刷新列表」 |

其它边界：

- 定时备份执行有 `running` 门闩，tick 与回前台并发时最多跑一次；索引读改写在 `withIndexLock` 内串行化；
- 旧版本清理是"尽力而为"：单条删除失败只记 warn，不让本次备份失败；
- 页面卸载清理 `setInterval` 与 `settings:changed` 订阅；调度器的 `visibilitychange` 监听由模块级 `listenersBound` 保证只绑一次，`stopBackupScheduler()` 可完全解绑（测试用 `__resetBackupScheduler`）；
- 定时备份失败不写 `lastScheduledAt`，因此下次 tick 会再次尝试（不会"失败即跳过一整天"）；成功后才推进时间点，避免同一计划点重复补跑。
